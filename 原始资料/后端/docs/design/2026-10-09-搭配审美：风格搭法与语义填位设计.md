## 一、背景：内测反馈与实测证据

内测用户反馈推荐"低级错误多、看着无厘头"，典型例子：**牛仔背带裤配牛仔背心（马甲）**。

### 1.1 实测：错误搭配几乎和正常搭配同分

用临时测试按现有引擎打分（日常、20°C、未设性别）：

| 组合 | 总分 | 引擎给出的理由 |
|---|---|---|
| 牛仔背心 + 牛仔背带裤 + 小白鞋 | **84.3** | "全身中性色，稳妥耐看""主体都偏休闲风" |
| 白T + 牛仔背带裤 + 小白鞋 | 88.0 | "牛仔蓝+白，清爽" |

错误搭配只低 3.7 分，而且理由在夸它。另外发现：**白衬衫 + 牛仔裤 + 小白鞋只有 76.0 分，低于牛仔衬衫 + 牛仔裤（修复前约 86.8）**，原因是风格标签"通勤/正式"与"休闲"被判为不一致。

### 1.2 实测：真实衣柜的标签状况（本地库，266 件在柜衣物，1 名内测用户）

| 字段 | 不同写法数 | 问题 |

| 主色 | 45 | 米白、奶油白、浅灰蓝…… |
| 图案 | 61 | 混入装饰（"蝴蝶结装饰""蕾丝装饰"） |

## 二、诊断：为什么总是"测一次一堆问题、反反复复"

1. **"背心"一词两义**：`OutfitRules` 把背心、马甲都判为上装，牛仔马甲被当成背带裤里面的上衣，结构检查放行。（已在第三节修复）
2. **识别词表粗**：品类示例缺马甲、背带裤、吊带；风格只有 7 个大类，几乎人人"休闲"，风格维度失去区分作用。
3. **没有材质与层次规则**：DENIM 被列为中性色，两件牛仔反而得到"全身中性色"加分。（已修复牛仔叠牛仔）
4. **打分只检查"哪里冲突"，不评价"好不好看"**：七个维度都是排雷，没有比例、焦点、整体意图；不冲突就是 80+ 分。
5. **模板不参与生成**：74 条模板在资源文件里全部是待审核，最多只加 5 分；候选靠"上装×下装×鞋"全排列，挑不出毛病就推荐，看起来没有章法。
6. **规则全局统一、不分风格**：同一个组合在不同风格里好坏相反（见第四节），一套全局规则只能不停打补丁，越补越乱。
7. **质量只能靠人测出来**：考试题仅 12 道、29 件衣物，没有在上线前系统检查"推出来的东西像不像人搭的"。

第 6、7 条是"反复"的根本原因：规则空间是开放的，而发现问题的唯一手段是人工测试。

## 四、好看的本质：四层模型

好看的穿搭确实由规则构成，但不是一条条"如果……就……"。它是四种性质不同的东西叠在一起：

**第一层：底线（硬规则，数量少，几乎人人认同）**
物理与场合上的"不可能"：马甲不能当背带裤的内搭；拖鞋不去面试；零下不穿短袖。可以列完。

**第二层：视觉原理（模糊规则，是程度不是对错）**
- 色彩：全身主色不超过三种，中性色打底，颜色前后呼应。
- 比例：上宽下窄或上窄下宽，上短下长，有腰线，露脚踝/手腕显轻。
- 焦点：一套只有一个主角（亮色、大花纹或特殊材质），其余衬托；两个主角会打架。
- 统一与对比：质感、正式程度要么统一，要么有意对比，最怕随机混。
这些只能打分，且彼此拉扯（太对比显乱、太统一显闷）。

**第三层：风格（约定俗成的搭配惯例）**
法式、JK、洛丽塔、街头不是从原理推出来的，而是文化约定。人靠"像不像典型样子"认风格，因此风格本质是**一组典型范例 + 每个位置允许怎么替换**：
- 法式 ≈ 条纹衫 + 直筒牛仔裤 + 乐福鞋
- JK ≈ 水手服 + 百褶裙 + 小皮鞋 + 中筒袜
- 街头 ≈ 宽松卫衣 + 工装裤 + 球鞋

**关键：第三层会改写第二层。** 牛仔叠牛仔在通勤里是错，在美式复古里是招牌；运动鞋配西装在正式场合是错，在街头风里加分；洛丽塔一身蕾丝、蝴蝶结、多元素，按"单一焦点"会被扣分，但在洛丽塔里是对的。**同一组合好不好看，取决于它属于哪种风格。**

**第四层：熟悉感、潮流与个人（数据，不是规则）**
"大众审美"有很大一部分是"见得多就觉得对"：常见组合显自然，罕见组合显怪。所以潮流会变，常见搭配的统计本身就是审美依据。再叠加个人身材、肤色、喜好，只能从反馈学。

### 4.1 对照现有引擎

| 层 | 现有引擎 | 后果 |
|---|---|---|
| 底线 | 有，但没列全 | 偶发低级错误 |
| 视觉原理 | 只有色彩；无比例、焦点 | 配色还行，整体无章法 |
| 风格 | **完全没有**（模板最多 +5 分） | 每套都是"不违规的随机组合"，看不出意图 |
| 熟悉感与个人 | 有个人反馈；无"常见组合"统计 | 推不出"一看就是那么回事"的组合 |

**一句话：好看 = 守住底线 + 看得出是故意的（属于某种风格）+ 执行干净（比例、焦点、色彩）+ 合这个人。**

## 五、讨论过但放弃或推迟的方案

| 方案 | 结论 | 原因 |
|---|---|---|
| 自己训练搭配兼容度模型（CLIP 向量 + 小网络，离线训练、ONNX 本地推理） | **推迟进后续池** | 需要大量标注数据和训练流程，几周起步才能学会明显错误，投入产出比差；新方案下不是必需 |

## 六、标签策略：只严管两样，其余保持开放

语义填位（第八节）让标签治理的负担大幅下降：

| 类别 | 字段 | 要求 | 原因 |
|---|---|---|---|
| **必须准、必须封闭** | 穿着位置（上装/内搭/外层/下装/一体/背带/鞋/帽/头饰/包/手持/袜/围巾……，`OutfitRules.Role`） | 由品类按固定顺序推导；推导不出为 `OTHER`，不进推荐并提示确认 | 位置错了衣服会填进错的位置，语义无法补救 |
| | 颜色系（12 个，`MetadataValues.colorFamily` / `FeatureTables.family`） | 已有归并，P4 实测取色可校对 | 搭法的颜色关系、色彩原理依赖它 |
| **推导用（代码算，不问模型）** | 材质族（牛仔、针织、蕾丝、皮革、毛呢、雪纺纱、丝缎、羽绒、运动面料）、保暖、正式度、季节 | 由品类 + 纹理 + 袖长 + 长度用关键词表推导；推导不出为未知 | 模型猜厚薄、季节本来就不可靠（一半以上未知）；风格允许项（8.2）需要材质族 |
| **开放（只进语义描述卡）** | 品类原话、图案、纹理、版型、领型、门襟、装饰细节、风格词、可见文字、品牌、用户自定义标签 | 不限写法，不防自创 | 只用于语义匹配和搜索；写法乱不影响匹配，这正是语义的长处 |

- **用户自定义标签**（如"约会战袍""妈妈送的"）：单独一栏"我的标签"，拼进语义描述卡 `GarmentCard`，用于搜索与"穿那件约会战袍"的定位；不进审美规则。
- **语义搜索**：保留（bge 文本向量 + Chinese-CLIP 以文搜图），不新增投入。它管"找衣服"，现在也管"往搭法位置填衣服"，不管"搭不搭"。
- 以后若某条风格允许项或原理规则需要新的封闭字段，再按需加推导，不做一次性大改。

```

  │
  ├─① 选搭法：按风格、场合、季节、人群筛出候选搭法（第八节）
```

## 八、搭法与语义填位

### 8.1 搭法格式（草案）

在现有模板（`OutfitTemplates`，74 条）基础上扩展，同一套审核流程（`/admin/templates`，D31）：

```jsonc
{
  "id": "french-stripe-straight-denim",
  "style": "法式",                       // 第十二节风格清单中的一个
  "text": "条纹上衣配直筒牛仔裤和乐福鞋，法式日常",
  "occasions": ["日常", "约会"], "seasons": ["春", "秋"], "audience": [],   // 沿用 P4 Meta
  "slots": [
    { "position": "TOP",    "describe": ["条纹T恤", "条纹衬衫", "海魂衫"], "color": "any" },
    { "position": "BOTTOM", "describe": ["直筒牛仔裤", "九分直筒牛仔裤"], "color": "any" },
    { "position": "SHOES",  "describe": ["乐福鞋", "玛丽珍鞋", "芭蕾平底鞋"] },
    { "position": "OUTER",  "describe": ["米色风衣", "藏蓝针织开衫"], "optional": true },
    { "position": "BAG",    "describe": ["编织包", "小号皮质托特包"], "optional": true }
  ],
  "colorRelation": "NEUTRAL_PLUS_ONE",   // 可选：同色系 / 中性+一点色 / 对比 / 不限
  "allow": ["double-denim"],             // 该搭法额外放宽的原理项（通常继承风格）
  "kind": "CLASSIC", "reference": "", "reviewStatus": "PENDING_REVIEW"
}
```

**描述的写法规则**（来自 8.3 实测，作为起草约束与审核要点）：
- 每个位置写 1~3 个**具体物件**：品类 + 颜色/图案/款式，如"黑色百褶半身裙""条纹T恤"。
- **禁止**在位置描述里写风格形容词（"甜美的上衣""法式连衣裙"），风格只写在搭法的 `style` 上。
- 位置必须用 `position` 硬指定，不能靠描述暗示。

### 8.2 风格允许项

每种风格带一组对第二层原理的放宽或收紧，搭法默认继承，可在搭法上补充：

| 风格 | 允许项示例 |
|---|---|
| 街头潮流 | 运动鞋配西装外套不扣分；宽松上装配宽松下装不扣比例分 |
| 美式复古/工装 | 牛仔叠牛仔不扣分 |
| 洛丽塔、哥特洛丽塔 | 焦点数量放宽（蕾丝、蝴蝶结、头饰、印花可同时出现）；必须有头饰或袜子位时才算完整 |
| JK、学院 | 格纹+纯色固定组合加分；中筒袜/小皮鞋视为该风格的标志位置 |
| 通勤、正式 | 收紧：叠牛仔、强花纹、运动鞋按原规则扣分 |
| 极简 | 收紧：强调色 ≤1，花纹 ≤ 弱 |

全局规则成为"默认风格"的参数；选定风格后读该风格的允许项再打分。这正是"同一组合在不同风格里好坏相反"的处理方式，避免继续打全局补丁。

### 8.3 实测：语义填位在真实衣柜上的准确度

2026-10-09 用本地文本向量（bge-small-zh，`GARMENT_EMBEDDING` 已有 266 件）和 Chinese-CLIP（`GARMENT_IMAGE_EMBEDDING`，文本塔 fp32）对 14 条描述在全衣柜（不分位置）检索前 5：

| 描述 | 结果 | 结论 |
|---|---|---|
| 白色T恤、牛仔裤、黑色半身裙、百褶裙、格纹半身裙、针织开衫、玛丽珍鞋、西装外套 | 前 5 基本全对；"牛仔裤"没有串到牛仔背带裤、牛仔马甲 | **具体物件描述可靠** |
| 条纹上衣 | 文本第 3 名为条纹风衣；看图第 2 名为条纹连衣裙 | **会串位置**，必须位置硬筛 |
| 白色运动鞋（看图） | 混入靴子、长裤 | 串位置 |

### 8.4 填位算法

1. **预计算位置描述向量**：搭法审核通过（或加载）时，用本地文本模型与 CLIP 文本塔把每条描述编码一次，按模型版本缓存（库表或内存）。推荐时不需要加载 CLIP 文本塔，避免 4c4g 内存压力（衣物侧向量已在库中）。
2. **位置硬筛**：只看 `role` 等于该位置的在柜衣物（沿用召回阶段的排除：用户排除、冷却、避开颜色、性别底线）。
3. **综合相似度**：`s = α·cos(描述文本向量, 衣物文本向量) + β·cos(描述CLIP向量, 衣物图像向量)`，一个位置多条描述取最大值。α、β 初值 0.6/0.4，由试填校准；某路向量缺失时只用另一路；都缺失时退回关键词匹配（现有 `accepts` 的品类关键词）。
4. **颜色约束**：搭法写了颜色系或颜色关系时作为硬筛或加分（按 `colorRelation`）。
5. **取候选**：每个位置取 `s ≥ 最低门槛` 且与第一名差距 ≤ δ 的前 k 件（k=3）。
6. **组装**：各位置候选做束搜索（宽度约 20），每个组合送评委打分；可选位置缺失不扣分，必选位置缺失则记为"差一件"候选。
7. **结果**：每套带上"来自搭法 X""每个位置匹配了哪件、相似度多少"，供解释接口与试填工具展示。

规模估算：300 条搭法 × 平均 4 个位置 × 每位置约 50 件同位置衣物 × 512 维点积 ≈ 6 万次点积，单线程数毫秒；组装与评委打分与现有引擎同量级。

### 8.5 与现有路径的衔接

- 推荐主路径改为"搭法优先"；现有全排列路径保留为兜底，结果标注"自由组合"，同样受底线与评委约束。
- "今日灵感"（D35）已经是"搭法做骨架、衣物填位"，直接换用新的填位算法。
- 模板加分（`template` 规则 +1~+5）在搭法路径中不再重复计；自由组合路径命中搭法时仍加分。
- "换一件"在同一搭法、同一位置的候选中替换；"换一批"换搭法。
- 必选衣物：只选含该衣物所在位置、且该衣物相似度过门槛的搭法；都不行时退回自由组合。

## 十三、质量闭环：在上线前发现问题

这是解决"测一次一堆问题、反反复复"的关键。

1. **试填工具（管理页）**：每条搭法在若干测试衣柜（`Wardrobes`、考试题衣柜、合成的典型衣柜）和授权的内测衣柜上自动试填，逐位置列出匹配到的衣物与相似度，标记"无匹配""匹配可疑（低于门槛或与第一名差距大）"。管理员只需改描述，不碰代码。审核通过前必须看过试填结果。
2. **填位考试题**：新增一组"描述 → 应匹配/不应匹配的衣物"题（如"牛仔裤"不应匹配牛仔背带裤），与 `GoldenOutfitsTest` 一样每次构建都跑；失败时先判断题与描述谁错，不得为通过而删题。
3. **内测反馈一键转考题**：管理员看到"这套不对"，解释接口列出这套来自哪条搭法、每个位置怎么匹配的、评委各项分数；修正后一键把该组合存为坏搭配考试题（衣物只存属性，不存图片和名称）。
4. **发布门禁**：搭法库或评委参数变更时，跑全部考试题 + 试填统计（无匹配率、可疑率），超出阈值不发布。
5. **人工投入**：管理员每周约 200 条判断（D55），优先用于：审核新搭法的试填结果、复核可疑匹配、处理内测"这套不对"。

## 十七、补充实测：评委没有区分度

2026-10-10 用考试题衣柜（`golden-outfits.json`，32 件，未测色、无版型和长度字段）枚举全部"上装×下装×鞋"与"连衣裙×鞋"，共 861 套，不违反硬规则的全部打分（女性、无画像）：

| 场景 | ≥60 分 | ≥80 分 | 中位数 | 最高分 | 并列最高分 | 距最高分 2 分以内 | 前 10%（86 套）里不同分数的个数 |
|---|---|---|---|---|---|---|---|
| 日常 20°C | 92% | 29% | 75.5 | 88.0 | **17 套** | 48 套 | **13 个** |
| 通勤 18°C | 76% | 18% | 70.8 | 90.5 | 7 套 | 20 套 | 43 个 |
| 约会 22°C | 82% | 29% | 74.0 | 88.0 | 2 套 | 16 套 | 35 个 |

各维度"得分 ≥0.9"的比例：**色彩 95%**，风格 36%（且前排全部为 1.0），冷暖 67%～76%。没有画像和语义时，相关度、个人偏好、新鲜度是常数。**排在前面的组合之间，真正在变的只有"场景"一个维度**，也就是平均正式程度离场景目标有多远。

典型例子（日常 20°C）：

| 组合 | 总分 | 说明 |
|---|---|---|
| 藏蓝毛衣 + 灰格纹长裤 + 黑凉鞋 | **88.0**（并列第一） | 色彩 1.0、风格 1.0、保暖值合适；毛衣配凉鞋的季节感冲突没有任何规则管 |
| 白T + 牛仔背带裤 + 黄色运动鞋 | 88.0 | — |
| 白T + 牛仔裤 + 小白鞋 | 87.4 | 公认的经典，输给上面两套 |

17 套并列 88.0 时，`pool.sort` 的第二排序键是组合 key（`StyleProfile.outfitKey`，由衣物 id 算出的 UUID 哈希），**最终谁排第一取决于哈希值的字典序，与好看与否无关**。

**结论**：问题不只是"规则不够"，而是打分结构本身——各维度从高分起步、只在发现问题时扣分，没有发现问题就接近满分；"好看"没有任何加分通道。补再多排雷规则，也只能把坏的压下去，没法把好的抬上来。真实衣柜有实测色值，`precise` 规则会带来 ±0.05～0.2 的变化，但折算到总分只有 1～5 分，同样不足以拉开差距。

## 十八、评委结构：配色安全 + 审美组

把"不出错"和"好看"分成两组，好看必须有依据才拿分：

| 组 | 维度 | 日常权重（现→新） | 计分方式 |
|---|---|---|---|
| 不出错 | 配色安全（原"色彩"） | 25 → 15 | 起步 0.9，只扣分：强调色过多、撞色、两件强花纹、条纹配格纹、反馈过不搭的颜色（现有规则原样保留） |
| | 冷暖 | 20 → 17 | 不变 |
| | 风格 | 15 → 12 | 不变；S3 起改为"与所选搭法风格的一致度"（第九节） |
| | 场景 | 15 → 12 | 不变 |
| | 需求相关 / 个人偏好 / 新鲜度 | 10 / 10 / 5 → 8 / 8 / 3 | 不变 |
| **审美（新）** | 配色手法 | 10 | 识别出配色方案并评执行质量（第十九节）；**没有明确方案只得 0.3** |
| | 比例与廓形 | 7 | 第二十节；字段缺失记 0.5（中值，不奖不罚） |
| | 焦点 | 4 | 第九节焦点项按视觉重量细化（第十九节 19.4） |
| | 呼应与季节感 | 4 | 第二十一节 |

- 其他场景按同样比例缩放：从各场景现有权重中统一拿出 25 分给审美组，配色安全在运动/户外场景降到 10。
- 审美组每一项都输出 `Line(依据, 正/负)`，与现有维度格式相同，解释接口和卡片无需改结构。
- **并列打破**：`pool.sort` 的次序改为 总分 → 审美组得分 → 搭法填位置信度（S1 后）→ 个人偏好 → key。key 只在前面完全相同时起作用。
- 权重是初值，第二十三节的成对标定后再调整；调整同样写进 `feature-tables.json` 并带版本号。

## 十九、配色细则（用实测色值，缺失时退回颜色名）

现有实测数据：每件展示图的 `palette` 为 k=3 的 CIELAB 色块 `Swatch(L, a, b, ratio)`，`chroma < 12` 视为中性（`ColorScience.NEUTRAL_CHROMA`）。

### 19.1 全身色板：按面积加权

一件衣服在整套里占的面积不同，红鞋和红上衣不能同等看待。面积系数（初值，配置在 `feature-tables.json` 的 `aesthetic.area`）：

| 位置 | 系数 |
|---|---|
| 连衣裙/连体 `ONE_PIECE` | 0.65 |
| 背带裙/背带裤 `OVERALL` | 0.45 |
| 上装 `TOP` / 下装 `BOTTOM` | 各 0.35 |
| 外层 `OUTER`（只在用户指定穿外层时进入打分） | 0.45，其下的上装降为 0.2 |
| 鞋 `SHOES` | 0.08 |
| 配件 | 不计（D45：配件不改总分） |

全身色板 = 每件的每个色块，面积 = 位置系数 × 色块 `ratio`。**视觉重量** = 面积 × min(1.5, chroma / 40)。现有"强调色个数"规则保留在配色安全里；配色手法看的是面积和重量。

### 19.2 配色方案识别

按顺序判断，命中第一个即为本套方案，依据里写出方案名：

| 方案 | 判定（实测） | 基础分 | 依据示例 |
|---|---|---|---|
| 同色系深浅 | 所有有彩色块色相差 ≤ 25°，且全身明度跨度 ≥ 20 | 0.9 | "同色系深浅搭配：雾蓝衬衫配藏蓝半裙" |
| 中性色 + 一处点缀 | 有彩色总面积占 8%～35%，色相集中在一组 | 0.85 | "中性色打底，红色小面积点缀" |
| 全中性有层次 | 全部中性，明度跨度 ≥ 25 | 0.8 | "黑白灰分明，干净利落" |
| 邻近色 | 有彩色色相差 ≤ 60°，饱和度接近（chroma 差 ≤ 20） | 0.75 | "黄绿邻近色，过渡自然" |
| 对比色点缀 | 两组色相差 ≥ 150°，较小一组面积 ≤ 15% | 0.75 | "蓝色主体配一点橙，对比提神" |
| 全中性无层次 | 全部中性，明度跨度 < 10 | 0.5（同色一身 + 材质不同时 0.7） | "全身颜色和深浅都接近，略平" |
| 大面积撞色 | 两组色相差 ≥ 90°，各占 ≥ 25%，chroma 都 ≥ 35 | 0.3（风格允许时 0.7，见 8.2） | "大面积撞色" |
| 无明确方案 | 以上都不符合 | 0.3 | "配色没有明确思路" |

### 19.3 执行质量修正（加减在基础分上）

| 项 | 规则 | 修正 |
|---|---|---|
| 呼应 | 两件不相邻衣物的任意色块 ΔE（CIE76，`ColorScience.deltaE`）< 12，且该色不是大面积中性色。例：鞋子和上衣印花里的红 | +0.1，"鞋子呼应上衣印花里的红" |
| 饱和度统一 | 有彩色块里同时存在灰调色（chroma 12～25）和高饱和色（≥ 50），且两者都占 ≥ 10% | −0.15，"灰调色和艳色放在一起显脏" |
| 中性色冷暖调 | 暖中性（b* > 6：米、驼、奶油白）与冷中性（b* < −2：冷灰、冷白）面积各 ≥ 20%；纯黑、纯白（chroma < 4）不参与 | −0.1，"暖米色与冷灰色色调不统一" |
| 明度结构 | 上下明度差 ≥ 30（现有规则）计入这里，不再加到配色安全 | +0.05 |

### 19.4 焦点：按视觉重量判断"主角"

细化第九节的焦点项。**主角**：视觉重量 ≥ 0.25 的有彩色块、强花纹（patternStrength = 2）且面积 ≥ 0.3，或特殊材质（蕾丝、亮片、丝缎、皮革，由第六节材质族推导）。**颜色相同（ΔE < 12）的多个主角算一组**，例如红鞋配红色印花。

| 情况 | 得分 | 依据 |
|---|---|---|
| 恰好一组主角 | 1.0 | "红色印花是主角，其余衬托" |
| 没有主角 | 0.7（极简风格 0.9） | — |
| 两组以上 | 0.3（洛丽塔等风格放宽，见 8.2） | "印花上衣和亮色裤子都很抢眼，焦点打架" |

### 19.5 未测色时

退回按颜色名判断：中性色系与有彩色系按 `FeatureTables.Family` 归组，面积仍按 19.1 的位置系数，方案仍按 19.2 识别，但只能识别"中性 + 一处点缀""全中性"和"同色系"三种（颜色名分辨不出邻近色和对比色）。基础分乘以 0.8，依据加注"按颜色名判断"。冷暖调与饱和度统一不评。

## 二十一、季节感与材质一致

针对第十七节的"毛衣配凉鞋 88 分"。现有"上下冷暖协调"只比较上装和下装，鞋、外层不参与。

| 规则 | 判定 | 扣分 |
|---|---|---|
| 季节感冲突 | 任意两件可穿衣物的季节标签都已知且没有交集（毛衣 {秋, 冬} 与凉鞋 {夏}）；季节未知时退回保暖值差 ≥ 2.5（现有上下规则推广到鞋与外层） | 呼应与季节感维度记 0.2；配合扣分规则 `season.mismatch` −6，"毛衣配凉鞋，季节感冲突" |
| 季节材质冲突 | 毛呢、羽绒、厚针织与雪纺、纱、亮面丝缎同时出现（材质族由第六节推导） | −4，"厚毛呢配薄纱，季节感不统一"；洛丽塔、复古放宽 |
| 季节感一致 | 全部可穿衣物季节标签有共同季节，且与当前季节一致 | 呼应与季节感维度 +0.2 |

薄针织（厚薄为"薄"）配凉鞋属于春秋过渡，按保暖值判断不会触发。

## 二十二、一页三套：给出"不同的好"

现在的多样化只看衣物重复（共用一件降 30%、两件降 70%）。三套可能都是"全身中性、无主角"，只是换了衣服。

- 在 `overlapFactor` 之外加**方案重复系数**：与已选的某套配色方案相同且搭法相同（S1 后）× 0.9，只是方案相同 × 0.95。
- 第一套取总分最高（稳妥）；第二套优先选不同配色方案或不同搭法（换一种思路）；第三套保持现有"新尝试"位（D20）。
- 每套卡片的第一条亮点改为**手法标题**，来自命中的方案、比例规则或搭法名，例如"同色系深浅""上短下长""白T牛仔经典"。

## 二十三、审美标定：成对判断与区分度守护

### 23.1 成对判断集

- 管理员每周约 200 条判断（D55）中，拿出一部分做成对比较：同一意图下两套，选"A 更好看 / B 更好看 / 差不多"。
- **优先出分数接近的对**（总分差 < 5）：这类对最能暴露评委分不出的地方，比随机抽样信息量大。
- 来源：测试衣柜、考试题衣柜、授权的内测衣柜（只存衣物属性，不存图片和名称，与第十三节第 3 条相同）。

### 23.2 指标与发布门禁

| 指标 | 含义 | 初始目标 |
|---|---|---|
| 成对一致率 | 非"差不多"的对里，评委分高的一方与人选一致的比例 | 先记录当前基线；改造后高于基线 10 个百分点以上 |
| 区分度：并列最高分 | 固定衣柜、固定意图下，与最高分完全相同的套数 | ≤ 3（现在日常 20°C 为 17） |
| 区分度：前 10% 的不同分数个数占比 | — | ≥ 50%（现在日常 20°C 为 13/86 ≈ 15%） |
| 配色饱和度 | 配色手法维度 ≥ 0.9 的比例 | ≤ 40%（现色彩维度为 95%） |

区分度三项做成自动化测试 `AestheticSpreadTest`，与 `GoldenOutfitsTest` 一样每次构建都跑，防止以后改规则又退回"一律高分"。成对一致率在发布门禁里检查，下降超过 2 个百分点不发布（与第十三节第 4 条合并）。

### 23.3 权重拟合（可选，需单独确认）

成对判断满 300 条后，离线按维度差做逻辑回归（Bradley–Terry），向当前权重收缩，得到建议权重；以 PR 形式改 `feature-tables.json`，人工审核后才生效。运行时仍是固定权重的代码计算，零模型调用。这是总设计 10.1 后续池里"学习权重（D25）"的落地方式，**本篇只提议，不默认启动**。

### 23.4 推荐快照对比页

改规则前后，用脚本在测试衣柜和考试题衣柜上各跑一组固定意图，输出离线 HTML：每个意图前 3 套并排显示（色块示意 + 衣物名 + 分数 + 手法标题），标出新旧版排名变化。做法同图像评估的看图检查页。改规则的 PR 附上这页，评审时一眼能看出"哪些套被抬上来、哪些被压下去"，不用等内测反馈。

### 23.5 新增考试题（每条规则配正反题）

| 题 | 好 | 坏 |
|---|---|---|
| 季节感 | 毛衣 + 长裤 + 短靴 | 毛衣 + 长裤 + 凉鞋 |
| 同色系深浅 | 浅蓝衬衫 + 藏蓝半裙 | 同色同深浅（需测色衣柜） |
| 点缀面积 | 中性色主体 + 红鞋 | 红上衣 + 绿裤（已有） |
| 比例 | 短款针织 + 高腰阔腿裤 | 长款卫衣 + 阔腿长裤 |
| 塞衣角 | 衬衫 + 高腰半裙（带"塞进去"建议） | 同组合在不可塞的长卫衣上 |
| 经典优先 | 白T + 牛仔裤 + 小白鞋 | 第十七节中不应并列第一的组合 |

考试题衣柜需要补字段（`fit`、`garmentLength`）和少量带实测色块的衣物；测色衣物的色块直接写在题目文件里，不依赖图片。

## 二十四、解释：说出用了什么手法

- 亮点第一条是手法标题（第二十二节），第二条是具体依据，例如"同色系深浅 · 雾蓝衬衫配藏蓝半裙，深浅分明"。

- 穿法建议显示在亮点之后、提醒之前。

## 二十六、约定检查与风险（增强篇）

**约定**

- 零模型调用：全部由代码在已有字段和实测色值上计算。
- 不新增硬规则：所有新规则都是加权扣分或加分，并写依据。
- 配件不改总分（D45）：面积表不含配件；"鞋呼应"只用鞋（鞋是可穿衣物）。配件建议的挑选可复用 19.3 的呼应规则，但不影响总分。
- 不使用身材数据：比例只看衣物属性。
- 推荐相关改动同步更新总设计、本文和帮助文章 `04-recommend.md`；`GoldenOutfitsTest` 必须通过。

**风险**

| 风险 | 应对 |
|---|---|
| 加分通道让"花哨"组合上位 | 方案识别要求面积比合理（点缀 ≤ 35%）；大面积撞色默认低分；焦点两组以上低分 |

# 规则库篇（2026-10-10）：两张表 + 机制，作为审美的基础模型

**状态：设计提案，D70~D78 待用户确认。** 用户提出的基础模型是：一张**避坑表**，在有限标签里穷举所有不好的组合；一张**搭法表**，由 AI 批量生成，经人工、多模态模型或混合方式审批后不断增加；再加上加权、生命周期衰减等机制。本篇把这个模型落成统一的规则库，并补上它单独运转时缺的部分。

## 二十八、基础模型：两张表、一层原理、四种机制

| 组成 | 是什么 | 怎么增长 | 现有资产 |
|---|---|---|---|
| 避坑表 | 在封闭维度上**按维度对**穷举，每一格都有结论（包括"没问题"） | 模型一次填满，人工审有争议的格；之后靠反馈修订 | 鞋款×下装×场景矩阵、5 个撞色对、牛仔叠牛仔、正式度跨度、结构规则 |
| 搭法表 | 人认可的整套搭法，带风格、场合、位置描述 | 模型批量起草、样本转化、衣柜驱动、采纳挖掘；混合审批；持续增加 | 74 条模板（全部待审）、整套穿搭样本模板草稿、今日灵感 |
| 原理 | 不能列成表的整体性质：配色方案、比例、焦点、季节感 | 改代码和参数，不靠加条目 | 色彩维度、`precise`、冷暖协调；增强篇第十八~二十一节 |
| 机制 | 加权、生命周期、衰减、个人化、冲突仲裁 | 统计驱动 | 反馈三层（D28）、模板审核（D31）、流行有效期（D34） |

**为什么两张表不够，还要原理层**：

- 避坑表只能管"两件之间"的问题。三个强调色、两个焦点、上下都宽松这类整体问题，拆成两两组合是看不出来的。
- 搭法表覆盖不了所有衣柜，填不出搭法时只能退回自由组合。
- 一套组合如果既没踩避坑表、也没命中搭法表，两张表都不会给它任何信号，就会出现第十七节的"一律 88 分"。原理层对每套组合都能给出连续的分数，负责把这些组合拉开。

**对第五节结论的修订**：第五节曾把"两两避坑表穷举"限定在底线层，理由是规则空间开放。D56 把参与规则的标签收成了封闭维度（位置、颜色系，以及代码推导的材质族、保暖、正式度、季节），维度对的组合数因此变得有限，**软性的避坑规则也可以穷举**（第三十节）。穷举只限维度对，不穷举整套组合。

## 二十九、规则即数据：两张表用同一种格式

```jsonc
{
  "id": "avoid.color.red-green",
  "table": "AVOID",                              // AVOID 避坑 / PATTERN 搭法
  "match": { "dims": ["colorFamily", "colorFamily"], "values": ["RED", "GREEN"], "minArea": 0.2 },
  "verdict": "PENALTY", "points": -6,            // OK / PENALTY / SEVERE；搭法为正分，格式同第 8.1 节 slots
  "styles": { "多巴胺": { "points": -2 }, "节日": { "verdict": "OK" } },   // 风格列：放宽或收紧（8.2 风格允许项并入这里）
  "occasions": [], "audience": [], "seasons": [],
  "text": "{a}配{b}，大面积红绿撞色",
  "source": { "kind": "MODEL_DRAFT", "batch": "avoid-color-v1", "at": "2026-10-10" },  // MODEL_DRAFT / SAMPLE / CLOSET_GAP / ADOPTION / FEEDBACK / HUMAN
  "status": "ACTIVE", "version": 3,
  "lifecycle": { "kind": "CLASSIC" }             // 或 { "kind": "TREND", "peak": "2026-11-01", "halfLifeDays": 60 }
}
```

- 每条规则命中时产生 `RuleHit(id, delta, 依据)`，与现有 `RuleCatalog` 和解释接口一致。`RuleCatalog` 只保留硬规则和固定机制，表内规则从表加载。
- 存储方式沿用模板审核（D31）：规则文件随版本发布、不被改写；审核状态、分值调整存数据库，加载时叠加。
- 现有的鞋款矩阵、撞色对、经典配色对、牛仔叠牛仔先**原样迁入**，迁移前后由 `GoldenOutfitsTest` 和快照对比页（23.4）保证行为不变。

## 三十、避坑表：在封闭维度上按维度对穷举

### 30.1 维度与格数

| 子表 | 格数 | 现状 |
|---|---|---|
| 颜色系 × 颜色系（只管大面积，面积按 19.1 计算） | 78 | 5 个撞色对和 8 个经典对，其余 65 格空白 |
| 材质族 × 材质族 | 约 55 | 只有牛仔×牛仔 |
| 鞋款 × 下装/一体款 × 场景 | 7 × 8 × 8 | 基本填满（`shoe-bottom-v3`） |
| 季节 × 季节（任意两件） | 10 | 第二十一节 |
| 正式度档 × 正式度档 | 15 | 现在只有跨度 ≥ 2、≥ 3 两档 |
| 上装（松量×长度） × 下装（松量×长度×腰线） | 约 100 | 第二十节 R1~R3 |
| 花纹强度 × 花纹类型（两件之间） | 约 20 | 现有三条 |
| 位置 × 位置（叠穿） | 约 40 | 结构规则、马甲与背带 |
| **合计** | **约 900 格** | |

### 30.2 填表与审表

- **每格都要有明确结论**，包括 OK。这样表是完备的，可以算覆盖率：已审格 / 总格。未审格在打分时按 OK 处理，同时计数记入推荐日志，管理页显示为"未定"。
- 模型离线一次填满全部格：给出结论、分值、理由和自评把握，提示词里只有维度词表，没有用户数据。人工只审三类格：
  - 模型把握低的格；
  - 结论不是 OK 的格；
  - 与考试题或搭法表冲突的格。

  预计约 200 格需要人看，相当于一周的人工预算（D55）。
- **例外只开两种口子**：风格列和场景列。不开放任意三元组例外，避免表格膨胀。
- 避坑表不新增硬规则。SEVERE 仍是重扣分（D27），硬排除仍然只有结构、用户明确表达、男性×女款三类。
- 新填或改过的格先以**影子模式**运行（33.1）：只计算不计分，记录生效后会改变哪些排名，审过再生效。

## 三十一、搭法表：批量生成、混合审批、持续增长

### 31.1 四路来源

| 来源 | 做法 | 解决什么 |
|---|---|---|
| 模型批量起草 | 按覆盖网格补空格：风格 × 场合 × 季节 × 主体结构（上下装 / 一体 / 背带）。提示词只含风格清单、位置词表和写法规则（8.1），**不含用户衣物** | 冷启动、补齐风格 |
| 整套穿搭样本 | 沿用 D49：样本经审核生成模板草稿 | 来自真实穿搭 |
| 衣柜驱动 | 统计"孤儿衣物"，即在任何已生效搭法里都填不进去的衣物。按属性汇总（位置、品类、颜色系、风格；不含图片和名称），例如"9 件洛丽塔 JSK 没有搭法可用"，作为下一批起草的需求 | 用户的衣服用不上 |
| 采纳挖掘 | 用户反复采纳（D39 口径）的自由组合，抽象成属性模式（位置、品类关键词、颜色关系），达到支持度门槛后生成草稿。跨用户只在属性层面聚合（D21） | 发现规则以外的好搭配 |

### 31.2 三级审批

| 级 | 由谁做 | 做什么 | 结果 |
|---|---|---|---|
| 一、自动校验 | 代码 | 格式和位置合法；描述里没有风格形容词（8.1）；**与避坑表一致**：任一种填位组合命中 SEVERE 格且本风格没有放宽，则不通过；与已有搭法语义重复（描述向量余弦 ≥ 0.92）；试填成功率；试填结果的评委分 | 不通过直接退回，附原因 |
| 二、模型初审（可选，离线） | 多模态模型 | 对试填出的整套拼图**只做描述**：像不像所写风格、各位置是否看起来对、有没有明显问题。不下"好不好看"的结论。**只用测试衣柜的图片，不发送用户衣物** | 标出"存疑"条目和理由 |
| 三、人工终审 | 管理员 | 看试填拼图、模型描述、自动校验结果，选通过、退回或改描述 | "好看"由人决定（全身穿搭约定） |

- **整批通过**：管理员看过抽检样本后可以整批通过，前提是同时满足三条：同批里自动校验全过；模型没有标存疑；只是已通过搭法的近似变体（同风格同结构，只换颜色或单品）。
- 新风格、TREND、模型标存疑的条目必须逐条看。整批通过仍然是人的决定。

### 31.3 覆盖度看板

管理页按"风格 × 场合 × 季节 × 结构"显示每格的已生效搭法数、试填无匹配率、孤儿衣物数（按属性汇总）。下一批起草从缺口最大的格开始。

## 三十二、加权：四个系数相乘

**实际分值 = 基础分值 × 风格系数 × 健康度系数 × 个人系数**

| 系数 | 来源 | 范围 | 例子 |
|---|---|---|---|
| 基础分值 | 规则表的 `points` | — | 红绿撞色 −6 |
| 风格系数 | 规则的风格列（原 8.2 风格允许项） | 0 ~ 1.5 | 美式复古下牛仔叠牛仔 → 0 |
| 健康度系数 | 第三十三节统计 | 0.5 ~ 1.5 | 采纳率明显高于同类的搭法放大 |
| 个人系数 | 该用户对这条规则的倾向 | 0.4 ~ 1.5 | "你接受过牛仔叠牛仔，扣分减小" |

**个人系数是对现有机制的推广**。现在只有"图片风格混搭"有规则级的个人倾向（`mixLeaning`，`mixingBase` / `mixingLearned`），改为对所有表内规则都适用：

- 用户喜欢或采纳了一套被某条规则扣过分的组合，记一次"接受该规则"；
- 用户不喜欢一套被某条规则加过分的组合，记一次"不认可该规则"。

倾向键为 `R:<规则 id>`，衰减沿用 D28。底线规则不受个人系数影响；SEVERE 的个人系数下限是 0.5，保证再怎么接受也不会完全不扣。

## 三十三、生命周期与衰减

### 33.1 状态

```
DRAFT ──审批──▶ TRIAL ──曝光够、效果不差──▶ ACTIVE ◀──恢复── WATCH ──人工确认──▶ RETIRED
                                               └──效果持续偏低──▶ WATCH
```

| 状态 | 搭法 | 避坑格 |
|---|---|---|
| TRIAL 试运行 | 只出现在"新尝试"位（D20）和今日灵感，健康度系数固定为 1，累计曝光 | 影子模式：只计算不计分，记录会改变哪些排名 |
| ACTIVE 生效 | 正常参与 | 正常参与 |
| WATCH 观察 | 健康度下界 < 0.8，通知管理员，继续以降低后的权重运行 | 违背率高，进入"建议放宽"队列 |
| RETIRED 退役 | 管理员确认；TREND 过期自动退役 | 管理员确认 |

TRIAL → ACTIVE 的门槛初值：曝光 ≥ 30 次，且采纳率不显著低于同意图的基线。

### 33.2 健康度：每条规则自己的效果统计

| 规则类型 | 统计 | 用途 |
|---|---|---|
| 搭法、加分规则 | 命中该规则的组合的采纳率（D39 口径），与同意图、同场景、未命中该规则的组合比较，得到提升倍数；用 Beta 先验收缩，曝光少时接近 1 | 健康度系数 = 收缩后的提升倍数，限制在 0.5~1.5 |
| 避坑格 | 违背率：被该格扣分但仍被展示（指定衣物、新尝试位）且被采纳的比例；漏判率：通过该格却被标"这套不对"的比例 | 违背率高的格进"建议放宽"队列；漏判集中的格进"建议收紧"队列。**都不自动改，交人工** |

- 每晚离线计算一次健康度快照（`rule_health`，带版本）。推荐时只读快照，同一版本内结果确定；推荐日志记录快照版本，与现有 `tablesVersion` 一样可回放。
- 防止"越推越多"的偏差：只和同一意图分桶的基线比较；TRIAL 曝光设上限；先验收缩。

### 33.3 四种衰减

| 衰减 | 作用对象 | 方式 |
|---|---|---|
| 流行衰减 | TREND 搭法 | 现在过了 `validUntil` 就失效；改为峰值后按半衰期平滑衰减（初值 60 天），再到期退役 |
| 证据衰减 | 健康度统计 | 半衰期 90 天，流行变化能体现出来 |
| 个人反馈衰减 | 个人系数 | 沿用 D28：负面 30 天，正面 60 天 |
| 审美疲劳 | 某个用户最近反复看到的同一搭法或同一配色方案 | 近 14 天同一搭法出现 ≥ 3 次，下次 × 0.9，逐次递减，最低 0.7；和单品新鲜度（7 天）分开计算 |

## 三十四、冲突仲裁：谁说了算

一套组合同时命中多条规则时，按以下顺序生效，**高层可以覆盖低层**：

1. 底线：结构、用户明确表达、男性×女款（硬规则）
2. 用户这次的明确要求：指定衣物、想要的风格
3. 个人系数：用户反复表达过的接受或拒绝
4. 风格系数：当前搭法的风格，或用户想要的风格
5. 避坑表软规则
6. 原理
7. 搭法加分

- 同一层冲突时，条件更具体的格优先（带场景的格优先于不带的）。
- 审批时的一致性校验（31.2）保证搭法不会和避坑表"打架"，只能通过风格列合法放宽。
- 解释接口列出被覆盖的规则，例如"牛仔叠牛仔：美式复古风允许，不扣分"。

## 三十五、从反馈里发现新规则

- **每周离线任务**：
  1. 把"这套不对"、不喜欢、"换一件"里被换掉的组合，按维度对计数，与同期曝光相比算提升倍数。
  2. 超过门槛且支持度 ≥ k 的模式进入避坑表的"待审"：格子已存在的，提议调整分值；格子是 OK 且仍然高频被否定的，提示可能缺少一个维度。
- 采纳与点赞走 31.1 的采纳挖掘，生成搭法草稿。
- 管理员处理后可以一键转成考试题（第十三节第 3 条）。
- 内测期只有一位用户：门槛按单用户设定，**只提议，不自动改表**。

## 三十六、分期、指标与约定（规则库篇）

| 期 | 内容 | 验收 | 与 S 期的关系 |
|---|---|---|---|
| R1 规则即数据 | 统一格式；现有矩阵、撞色对、经典对、牛仔叠牛仔原样迁入；管理页按表浏览 | 迁移前后快照对比页无差异；考试题全过 | 与 S0.5 同期 |
| R2 避坑表补全 | 模型填满约 900 格；人工审争议格；影子模式；覆盖率看板 | 已审覆盖率 ≥ 80%；影子模式报告经人工确认后再生效 | S0.5 之后 |
| R3 搭法流水线 | 四路来源、三级审批、覆盖度看板、孤儿衣物统计 | 管理员能完成"起草—自动校验—试填—终审"全流程 | 扩展 S1、S2 |
| R4 生命周期与加权 | TRIAL/WATCH、健康度快照、流行衰减、审美疲劳、个人系数 | 健康度与个人系数都有依据文字，可在解释接口看到 | S3 之后，需有一定反馈量 |
| R5 规则发现 | 反馈聚类、待审队列 | 每周产出待审清单 | R4 之后 |

**指标**：避坑表覆盖率与已审率；搭法覆盖度与孤儿衣物比例；规则健康度分布；成对一致率与区分度（23.2）。

**约定检查**

- 推荐时零模型调用。模型只用于离线起草，以及可选的离线初审（只用测试衣柜）。
- 不向模型发送用户衣物资料：起草只给词表，初审只用测试衣柜，跨用户统计只在属性层面。
- 硬规则不增加；避坑表的 SEVERE 也是扣分。
- "好看"由管理员决定；模型只描述；搭法必须经审核才生效（含整批通过）。
- 推荐相关改动同步总设计、本文和帮助文章；`GoldenOutfitsTest` 必须通过。

**风险**

| 风险 | 应对 |
|---|---|
| 避坑表过严，误伤有意的创意搭配 | 风格列、个人系数、影子模式；违背率高的格进放宽队列 |
| 健康度被曝光偏差带偏（排得靠前的规则数据更多） | 同意图分桶比较、TRIAL 曝光上限、Beta 收缩、系数限制在 0.5~1.5 |
| 用户少，统计噪声大 | 最小曝光门槛；R4、R5 等有反馈量再启动；内测期只提议不自动改 |
| 模型起草的搭法千篇一律 | 覆盖网格、孤儿衣物、样本和采纳四路来源互补；语义去重 |
| 规则一多，解释变长 | 卡片只显示手法标题和最多 3 条依据；完整规则链在解释接口 |

# 上线篇（2026-10-10）：分配不均、边界情况与上线风险

**状态：设计提案，D79~D88 待用户确认。** 前三篇讲的都是"一套搭配好不好"。本篇讲的是"长期下来，推荐落在哪些衣服、哪些搭法、哪些人身上"，以及上线时会出什么问题。结论是：**现有引擎已经存在严重的曝光集中**，审美组和规则库如果不配套均衡机制，会把集中进一步放大。

## 三十八、实测：曝光高度集中

2026-10-10 用两个测试衣柜做模拟（临时测试，未提交；全部为女性、无画像）：

- **衣柜 A**：仿内测分布，167 件可穿衣物，其中连衣裙 61、长裤 24、半身裙 22、T恤 17、衬衫 10、针织 8、鞋 25；风格约一半为休闲。
- **衣柜 B**：`Wardrobes.generated(200, 42)`，190 件可穿衣物。

**模拟 1：16 种意图**（日常 / 通勤 / 约会 / 度假 × 8 / 14 / 20 / 26°C），每种取前 3 套：

| 衣柜 | 出现过的衣物 | 从未出现 | 连衣裙出现 | 基尼系数 | 出场最多的 10% 衣物占全部出场次数 |
|---|---|---|---|---|---|
| A | 49 / 167 | **118（71%）** | **5 / 61** | 0.81 | 58% |
| B | 51 / 190 | 139（73%） | 5 / 10 | 0.83 | 63% |

**模拟 2：同一意图（日常 20°C）连续 28 天**，近 7 天推荐过的衣物按现有新鲜度规则降权：

| 衣柜 | 28 天出现过的衣物 | 28 天里不同首页的个数 | 说明 |
|---|---|---|---|
| A | 49 / 167 | 14 | 连衣裙仍只有 5 件出现 |
| B | **31 / 190** | 11 | 有一件衣物出现在 84 套里的 45 套；**第 1 天的首页在第 5 天原样重复** |

**原因**（均已在代码和数据上核实）：

| # | 原因 | 证据 |
|---|---|---|
| 1 | **召回截断是确定的**：每个位置只取相关度前 K 件（上装 15、下装 10、连衣裙 8、鞋 6），相关度只随意图变化 | 衣柜 A 的 61 件连衣裙在 16 种意图里只有 32 件被召回过 |
| 2 | **连衣裙结构性吃亏**：外套只做建议、不计入保暖，连衣裙 + 鞋的保暖值天然偏低 | 衣柜 A 组合池里的平均冷暖分：14°C 时连衣裙 0.32、上下装 0.71；20°C 时 0.68 对 0.94 |
| 3 | **组合数量偏差**：同一次推荐，上下装有 15×10×7 = 1050 套，连衣裙只有 8×7 = 56 套。从多得多的样本里取最大值，最大值自然更高 | 衣柜 A 在 26°C 时连衣裙组合平均分（85.7）高于上下装（82.8），首页仍以上下装为主 |
| 4 | **万能单品**：中性色基础款能和很多衣物组合出高分，多样化只在同一页内生效，不跨天、不跨页 | 衣柜 B 一件衣物出现在 54% 的套里 |
| 5 | **新鲜度太弱**：只有召回相关度 −0.08 和新鲜度维度（权重 5），抵不过其他维度的差距 | 首页 4~5 天循环一次 |
| 6 | **闲置激活依赖穿着打卡**：没有打卡记录时不生效（`StyleProfileService`），而多数用户不打卡 | — |

**审美组会放大这个问题**：配色手法给"全中性有层次""中性色 + 一处点缀"高分，中性色基础款的优势会更大。搭法表的健康度和个人系数都是"出场越多、数据越多、权重越高"的正反馈。

## 三十九、曝光均衡设计

**原则：均衡不等于平均。** 百搭的衣服多出场是合理的。目标是：**每件"能搭得出合格整套"的衣物，在合理的周期内都有机会出场**；不为了均衡而推荐差搭配。

### 39.1 指标

"可推荐衣物"指至少有一套组合总分 ≥ 合格线（初值 70）且没有重扣分的衣物。

| 指标 | 定义 | 目标（初值） |
|---|---|---|
| 30 天覆盖率 | 可推荐衣物中，30 天内至少在首页出现一次的比例 | ≥ 80% |
| 集中度 | 可推荐衣物曝光次数的基尼系数 | ≤ 0.5 |
| 单品占比上限 | 14 天内任一衣物出现在首页套数中的比例 | ≤ 25%（用户指定的除外） |
| 首页重复 | 同一意图 7 天内首页完全相同的次数 | 0 |
| 结构平衡 | 首页里连衣裙套数占比 ÷ 衣柜主体里连衣裙占比 | 0.5 ~ 2（意图明确要裤装或裙装时不计） |

### 39.2 机制

| 机制 | 做法 | 解决 |
|---|---|---|
| **召回轮换名额** | 每个位置的 K 个名额里，约 70% 按相关度取，约 30% 从其余通过底线的衣物里按"曝光债"（39.3）再按当日种子轮换取。K 随该位置衣物数增长：K = clamp(基础值, ⌈1.5√n⌉, 上限)，61 件连衣裙约为 12 | 原因 1 |
| **外套计入保暖** | 冷天有外套建议时，按"主体 + 最合适的建议外套"计算冷暖分，卡片注明"需要加外套"；上下装同样适用 | 原因 2 |
| **按结构分组再交错** | 先把候选按主体结构（上下装 / 连衣裙 / 背带）分组，各组内按分数排名；首页按各组的组内百分位交错选，而不是全局取最大值。前提是该组最好的一套与全局最好的差距 ≤ 5 分 | 原因 3 |
| **跨天限流** | 14 天内曝光占比超过 25% 的衣物，在其他衣物有相近替代（差距 ≤ 3 分）时 × 0.85；用户指定的衣物不受影响 | 原因 4 |
| **近似并列轮换** | 总分差在 ε（初值 1.5 分）以内视为并列，并列时依次按曝光债、当日种子排序。种子 = 用户 + 日期 + 意图哈希，同一天刷新结果不变，换一天会变 | 原因 5，以及第十七节的并列 |
| **曝光债** | 见 39.3 | 原因 6 |
| **难搭单品提示** | 任何组合都达不到合格线的衣物，不硬推；在"整理衣柜"和今日灵感里提示"这件比较难搭：差一件白色T恤就能穿"（复用今日灵感的缺口提示） | 让"不出场"有解释 |

### 39.3 曝光债：不依赖打卡的轮换

- 每件衣物记录"上次出现在首页的日期"；新入柜的从入柜日期算起。
- 曝光债 = 距上次出现的天数。加分 = min(4, 0.15 × 天数)。
- 只在该组合没有重扣分、总分 ≥ 合格线时加分（与闲置激活相同的约束）。
- 依据写"这件 21 天没推荐过了"。
- 有打卡记录时，曝光债与闲置激活取较大者，不叠加。
- 新入柜 7 天内的衣物额外 +2，依据写"新入柜，先试试"。

### 39.4 搭法与规则层面的均衡

| 偏差 | 处理 |
|---|---|
| 宽泛的搭法（"任意上衣 + 任意裤子"）什么都能匹配，压过具体的搭法 | 搭法加分乘以具体度：每个位置有颜色、花纹或具体物件约束的比例；同一用户同一搭法 7 天内最多出现 2 次（与审美疲劳合并） |
| 健康度的马太效应 | 33.2 已有的分桶基线和 Beta 收缩；另加**位置校正**：第 1 张卡片天然被点得多，采纳率按卡片位置分别统计后再合并 |
| 单个重度用户主导全局统计 | 每个用户对每条规则的贡献按 1 票封顶；至少 5 个不同用户有数据，全局健康度才偏离 1 |
| 避坑格的幸存者偏差：被扣分的组合很少展示，违背率测不出来 | 用**用户自己搭的整套**做证据：搭台里保存的、打卡穿过的整套是用户选的，不是引擎选的，最适合检验避坑格 |
| 配色方案偏向中性色 | 方案基础分随"配色胆量"设置变化：保守时全中性更高，大胆时点缀与对比更高；首页方案多样化（第二十二节） |
| 搭法覆盖偏向女装、甜美风（来自内测衣柜分布） | 覆盖网格（31.3）加"人群"维度；按人群监控"搭法路径占比"和平均分，差距过大时优先起草 |

## 四十、边界情况清单

### 40.1 衣柜形态

| 情况 | 会发生什么 | 处理 |
|---|---|---|
| 极小衣柜（能组合的少于 3 套） | 每天一样，轮换也没用 | 如实提示"衣柜里能组合的不多，推荐会重复"；给缺口提示 |
| 只有连衣裙 / 只有上下装 / 没有鞋 | 结构分组只有一组；没鞋走现有"无鞋"降级 | 结构配额自动跳过不存在的结构 |
| 超大衣柜（500 件以上） | K 随 √n 增长，组合数膨胀 | 组合总数上限（初值 3000），超出时按位置相关度做束搜索；单次推荐耗时预算 300ms（4c4g） |
| 新用户只录了几件 | 没有画像、没有曝光历史 | 只用规则；曝光债从入柜日期起算，新衣物先出场 |
| 一部分衣物测过色、一部分没有 | **按 19.5 的 0.8 折扣，同一个衣柜里已测色的衣物会系统性占优**，造成新的分配不均 | **修订 19.5**：颜色名映射到代表色值（如"藏蓝" → L 25、a 2、b −25），所有衣物走同一套算法、不打折；是否实测只影响依据措辞 |
| 版型、长度等字段缺失 | 第二十节"缺失记 0.5"：已知好的总赢、已知差的反而输给未知 | **修订**：缺失时记该规则在已知衣物上的平均分，不奖不罚 |
| 几乎所有字段都是识图推测（内测用户手动修改为 0 件） | `evidence.inferred` 对绝大多数衣物都扣分，近似常数；识图有把握的衣物会略微占优 | 接受；在 39.1 指标里观察 |

### 40.2 时间与天气

| 情况 | 会发生什么 | 处理 |
|---|---|---|
| 温度在阈值附近（15°C 加裤袜/外套、28°C 偏热、<15°C 短裤偏冷） | 14.9°C 和 15.1°C 结果截然不同，前后两天来回跳 | 硬阈值改为 ±2°C 线性过渡 |
| 只有日期推断的季节 | 南方冬天 18°C 也按"冬"处理 | 优先用天气温度（D36）；只有日期时在提醒里注明 |
| 跨午夜 | 种子按日期变化，深夜会话中途结果改变 | 种子随推荐结果缓存固定；"换一批"沿用同一次结果 |

### 40.3 打分与规则

| 情况 | 会发生什么 | 处理 |
|---|---|---|
| **审美组与"新尝试"位冲突** | `exploration` 要求每个维度 ≥ 0.6，审美组"无明确方案"只有 0.3，**新尝试位几乎永远选不出来** | 审美组不参与这条检查 |
| **审美组变成满屏提醒** | 现有逻辑会把每个 < 0.6 的维度的第一条负面依据写进提醒，"配色没有明确思路"会出现在大多数卡片上 | 审美组只输出亮点和中性说明，不写提醒（缺少加分不是问题） |
| 分数尺度变化 | 权重一改，所有总分变化；依赖总分的阈值（考试题合格线 60、新尝试 0.8 倍、重扣分 10）都要重新校准；卡片若显示分数，用户会看到整体变化 | 新版本上线前按旧版本中位数做线性校准；阈值随版本存储 |
| 统计跨版本不可比 | `recommendation_log` 的维度向量换了键，`RecommendationStats` 和管理接口 KPI 会把新旧版本混在一起算 | 所有统计按 `ruleVersion` 分组；管理接口若新增字段，同步 `management-api.yaml` |
| 缓存混版本 | 结果缓存 30 分钟，键是"衣柜版本 + 意图"；规则表或健康度快照中途更新时，"换一批"会用新规则给旧候选打分 | 缓存键加上规则表版本、健康度快照版本和轮换种子 |
| **模板匹配的性能** | `templates.match` 对每套组合遍历全部已生效模板并回溯匹配。目前 74 条全部待审，**这段代码从未在有大量生效模板时跑过**。300 条生效 × 约 1100 套组合，每次推荐约 33 万次匹配 | 每次推荐先算一次"衣物 × 位置"的可填表，组合检查改为查表；模板按必需位置建索引 |
| 模型填的避坑表自相矛盾 | A×B 扣分但 B×A 不扣；正式度跨度不单调；相邻颜色系结论差很多 | 自动校验：对称性、单调性、相邻一致性，不通过的格退回 |
| 个人系数的归因 | 一套喜欢的组合同时被 3 条规则扣分，不知道用户接受的是哪一条 | 只有一条规则扣分 ≥ 3 时才归因；需要 ≥ 2 次独立事件才生效；每天每条规则最多记 1 次 |
| 审美疲劳与小衣柜 | 只有一条搭法能用时，疲劳把它降权，退回更差的自由组合，来回震荡 | 只有存在差距 ≤ 3 分的替代时才降权 |
| 搭法名不副实 | 填位相似度刚过最低门槛，卡片写"法式条纹"但衣服不是条纹 | 所有必选位置相似度都 ≥ 高门槛时才显示搭法名；否则按自由组合显示，不加搭法分 |
| 实测颜色名与识图颜色名不一致 | 依据里写"雾蓝"，衣物详情写"浅蓝"，用户困惑 | 文字一律用衣物自己的颜色名；实测值只参与计算 |
| 冷却过多 | 用户连续点不喜欢，一个位置的衣物全部进入冷却，召回为空 | 每个位置最多冷却 50% 的衣物，超过时提示而不是继续冷却；反馈学习每天限速 |
| 多人共用账号 | 个人系数、曝光债混在一起 | 有人物档案时按穿着人分开统计；否则按账号并在画像页说明 |
| 用户指定衣物 | 轮换、限流、疲劳都可能把它压下去 | 指定衣物不受任何均衡机制影响，但计入曝光 |

## 四十一、上线方案：影子运行、灰度、监控、回滚

| 步骤 | 内容 |
|---|---|
| 1. 离线 | 考试题、区分度测试、**曝光均衡模拟测试**（把第三十八节的模拟固化为 `ExposureBalanceTest`：在测试衣柜上模拟 28 天，断言 39.1 的指标）、快照对比页 |
| 2. 影子运行 | 新版本与旧版本同时计算，只展示旧版本，记录排名变化、耗时与 39.1 指标；数据不出服务器。至少 7 天 |
| 3. 灰度 | 先内测用户，再按用户哈希分批放量；同一用户固定在同一版本 |
| 4. 监控（每日） | 耗时 p95；空结果率；新尝试位填充率；39.1 全部指标；采纳率、点赞率、不喜欢率、"这套不对"率（按版本）；每张卡片平均提醒条数 |
| 5. 回滚 | 每个机制单独开关（审美组、轮换名额、曝光债、结构分组、外套计暖、搭法路径），规则表和权重按版本保留。管理接口只读，开关走应用配置或应用内管理页 |

告警条件（初值）：空结果率上升、耗时 p95 超过 300ms、基尼系数上升 0.1、采纳率下降超过 20%。告警只通知，回滚由人决定。
