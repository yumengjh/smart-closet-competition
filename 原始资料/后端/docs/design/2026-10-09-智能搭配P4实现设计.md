## 二、模板库扩展（D34）

### 2.1 字段

`outfit-templates.json` 每条模板在 P3 的 `id/text/bonus/enabled/reviewStatus/slots` 之外新增（全部可省略）：

| 字段 | 含义 | 省略时 |
|---|---|---|
| `kind` | `CLASSIC`（经典）或 `TREND`（流行） | `CLASSIC` |
| `audience` | `MALE`/`FEMALE` 列表 | 不限 |
| `seasons` | 适用季节；春秋互通 | 不限 |
| `occasions` | 适用场合（Intent.Occasion 名） | 不限 |
| `validFrom` / `validUntil` | 有效期（含首尾，业务时区） | 不限 |
| `reference` | 出处或说明，只给审核人看 | 空 |

槽位新增：`fitAny`（版型，读 `ruleFields.fit`）与 `patternMin`（最少花纹强度；"纯色上衣配花纹下装"的下装必须真有花纹，P4 截图自测时发现素色牛仔裤也能命中，已修正并加测试）。

规则：

- 用户性别未设置时**不会**被 `audience` 排除（与 P1.1 的性别原则一致：没设置就不做性别假设）。
- 流行模板过了 `validUntil` 自动不再命中、不再进今日灵感；审核页标"已过期"，不删数据，方便来年复审。
- 标签：命中经典模板显示"经典搭法：…"，流行模板显示"流行搭法：…"并加"流行"标签。
- 审核状态仍存 `outfit_template_review`，只覆盖状态、开关和加分；**定义**以资源文件为准，所以修正定义不需要迁移。

### 2.2 内容

draft-3 共 66 条：58 条经典（P3 的初稿补充了人群、季节、场合）+ 8 条流行草稿（美拉德、静奢、学院、工装、运动休闲、多巴胺、芭蕾风、新中式），有效期 2026-09-01 ~ 2027-03-31。全部为 `PENDING_REVIEW`，**管理员审核通过前不参与打分，也不进今日灵感**。流行内容由人整理、人审核，不联网抓取（见后续池"半自动流行"）。

## 三、今日灵感（D35）

### 3.1 算法（`Inspirations.build`，纯函数）

1. 可用衣物：去掉 `OTHER`、冷却中的单品、避开颜色。
2. 对每条已审核、已启用、`applies(性别, 季节, 今天)` 且场合相符（日常不限场合）的模板：
   - 每个槽位取符合条件的衣物，按个人倾向排序取前 5；
   - 恰好一个槽位为空 → 记为"差一件"提示；多于一个为空 → 跳过；
   - 全部有货 → 槽位做笛卡尔积，模板没覆盖的部分补齐（缺上装/下装各取倾向前 4，鞋取前 4 或"不配鞋"），每个组合先过硬规则，再用**同一套已审核模板**打分，取最高分。
3. 排序：总分 − 15（7 天内今日灵感用过的模板）+ `hash(用户|日期|模板)` 映射的 0~3 分抖动。同一天刷新结果不变，换一天会轮换。
4. 最多 3 套，主体（上下装/连衣裙）两两不同；"差一件"最多 3 条，最近用过的排后。
5. 每套的第一条亮点固定是来源模板的标签，标签首位"今日灵感"。

### 3.2 接口

`GET /api/recommendations/inspiration?temperatureC=`（可不填，不填按天气）返回：

```json
{ "view": { …与 POST /api/recommendations 相同的 View… },
  "ideas": [{ "key", "templateId", "text", "kind", "label" }],
  "gaps":  [{ "templateId", "text", "kind", "missing", "have": ["灰卫衣","小白鞋"], "hint": "差束脚/运动裤就能穿“…”" }],
  "approvedTemplates": 66, "applicableTemplates": 59 }
```

`view.runId` 是正常的推荐运行（30 分钟缓存），卡片上的详情、换一件、反馈、在搭台打开、今天穿了全部复用。日志来源记 `INSPIRATION`，并写 `recommendation_log.template_id` 供"7 天内用过"判断。

空状态文字：没有已审核模板 →"还没有审核通过的搭法…"；当季没有适用模板 →"当前季节没有适用的已审核搭法。"；有模板但凑不齐 →"衣柜里暂时凑不齐…"（此时"差一件"列表通常仍有内容）。

### 3.3 为什么这样做

- 用户说"不要黑箱乱搭"。灵感的骨架是人审核过的搭法，衣服是用户自己的，分数仍走白盒打分，所以每一套都能说清"按哪条搭法、为什么是这几件"。
- "差一件"只描述槽位条件（颜色/风格/品类），不推荐购买、不给链接（总设计非目标：不做购物推荐）。

## 四、天气（D36）

- `OpenMeteoWeather`：先用地理编码接口把设置页"常住城市"转成经纬度（进程内缓存；失败缓存 10 分钟），再取当天预报（缓存 1 小时）。`temperatureC = 0.6 × 最高 + 0.4 × 最低`，标签如"杭州 8~18°C"。
- `RecommendationWeather.apply(owner, intent)`：用户填了温度就不查；没填且有城市才查；任何失败返回原意图。`Intent.withWeather` 把温度来源记为 `WEATHER`，用户没指定季节时季节跟温度走；意图描述显示"12°C（杭州 8~18°C）"。
- 页面推荐、助手推荐（同一个 `recommend()`）和今日灵感都会套用。
- 配置：

```yaml
closet.weather.enabled: true            # 测试环境为 false，避免网络不确定
closet.weather.geocode-url: https://geocoding-api.open-meteo.com/v1/search
closet.weather.forecast-url: https://api.open-meteo.com/v1/forecast
closet.weather.timeout-seconds: 3
```

部署机器需要放行 `geocoding-api.open-meteo.com` 与 `api.open-meteo.com`；不放行时自动降级为"按日期推断季节"，卡片照常标注"未提供温度"。

## 五、精确取色（D37）

- `ColorScience.palette(BufferedImage)`：缩到 ≤96px，跳过 alpha < 128 的像素，在 CIELAB（D65）空间做 k=3 的 k-means（确定性初始化，12 轮），按面积排序输出 `Swatch(L, a, b, ratio)`；`chroma < 12` 视为中性色。算法名 `kmeans-lab-v1`。
- 没用 OpenCV：纯 Java 在 96px 缩略图上计算量很小，不新增原生依赖。
- `garment_color` 表按衣物存当时的 `display_asset_id`；展示图一换，旧结果自动不用并重算。`ColorIndexHandler`（任务队列 `COLOR_INDEX`，30 秒扫描，每批 100）在后台补算；读图失败写空调色板，不反复重试。
- 规则（`OutfitScorer.precise`，**只有整套每件都已测色时才生效**，否则行为与 P3 完全一致）：

| 条件 | 加减分 | 依据文字 |
|---|---|---|
| 上下明度差 ΔL ≥ 30 | +0.05 | 上下深浅分明，层次清楚 |
| 中性色几乎完全相同 | −0.05 | （单调） |
| 两件高饱和（C ≥ 35）色相差 ≥ 120° 且 ΔL < 25 | −0.2 | 实测对比过强 |
| 有彩色单品色相差 ≤ 30° | +0.05 | 实测色相相近，同色系和谐 |
| 识图说是彩色、实测饱和度很低 | 不再计入强调色 | X色实测饱和度很低，按中性色处理 |

## 六、好坏搭配考试题（D38）

`src/test/resources/recommend/golden-outfits.json`：29 件固定衣柜、12 道题，覆盖通勤、冷热、运动、约会、男性女款、配色、花纹、正式、居家、上下冷暖、高跟鞋。判定：

- 好搭配：不违反硬规则，且总分 ≥ `minGood`（60）；
- 坏搭配：被硬规则排除，或比该题最差的好搭配低至少 `margin`（5）分。

`GoldenOutfitsTest` 每题一个 `DynamicTest`，失败信息给出每套的分数与命中规则。规则改动导致失败时，先判断"题错了还是规则错了"再改。首次运行考出两处规则问题并已修正：

1. 花 T 配格纹裤得分接近好搭配 → 新增"大花纹再配条纹或格纹，容易显乱"−0.25；
2. 风格同时有"休闲/通勤"的卡其裤被当成西裤，导致配运动鞋被扣分 → `feature-tables.json` 新增 `casualTrouserStyles`，只有风格含通勤/正式且不含休闲/运动/户外的长裤才按西裤处理。

## 七、效果与成本统计（D39）

`GET /api/recommendations/stats?days=30`（1~365）：

- **效果**：推荐出的套数；采用数与采用率（采用 = 点赞、在搭台打开或 3 天内打卡穿过包含其全部衣物的一套）；点赞/点踩与好评率；在搭台打开；3 天内穿了；换一件次数与每套平均；按来源（推荐区/助手/今日灵感/换一批/换一件）分别统计。
- **成本**：助手消息数（`agent_daily_quota`）、识图/生图额度（`ai_daily_quota`）、助手调用次数与输入/输出 token（新表 `model_usage`，助手每轮 `done` 事件写一行，只记数字，不记内容；上游未报用量时记为"未上报"）、零模型推荐套数。

设置页"穿搭画像"分类底部新增"推荐效果与成本"卡片，可切换近 7/30/90 天。
