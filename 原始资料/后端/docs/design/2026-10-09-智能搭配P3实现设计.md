## 二、硬规则收敛（D27）

### 2.1 级别

`Compatibility.Level`：`OK`、`PENALTY`（一般扣分）、`SEVERE`（重扣，原 FORBIDDEN 格）、`FORBIDDEN`（只用于底线）。配置 `feature-tables.json` 的 `compatibility` 升为 `shoe-bottom-v2`，原 `"FORBIDDEN"` 值改写为 `"SEVERE"`；解析时旧值 `FORBIDDEN` 也按 SEVERE 读（`Level.parse`），旧配置不会意外变硬。

`Compatibility.check(items, intent, sex, mixing)` 每条 `Issue` 带 `rule`（规则 ID）和 `styles`（画风混搭时的风格组合）。不再读画像——P1.1 的"组合否定 ≥2 套即排除"整体并入反馈的同类组合层（第三节）。

### 2.2 硬规则只剩三类

`RecommendationEngine.violation(combo, …)` = `OutfitRules` 结构校验 + `Compatibility` 中的 FORBIDDEN（男性×确认女款、画风"总是不混"）。召回阶段的排除（本次排除衣物、避开颜色、冷却中、记忆"不穿"、男性女款、品类不明）各自写入规则追踪。

原来的硬性条件改为：

| 原规则 | 现在 | 位置 |
|---|---|---|
| 温度排除（`weatherExcluded`） | `OutfitScorer.weatherIssue` 给出依据文字；召回相关度 −0.3，整套每件 −20、合计最多 −30 | 召回 + 打分 |
| 正式程度跨度 ≥3 排除 | −20（规则 `formality.span`） | 打分 |
| 兼容表 FORBIDDEN | SEVERE −25（依据只是推测、或鞋与下装都由用户指定时降为 −4） | 打分 |
| 画风混搭 PENALTY/FORBID | 默认 AUTO 学习式扣分；FORBID 保留为硬（用户明确设置） | 打分 / 底线 |

### 2.3 "不配鞋"退路

放宽后出现一个风险：衣柜只有一双高跟鞋时，"衬衫 + 长裤 + 高跟鞋"会成为唯一组合重新出现（P1.1 问题 A 的原始案例）。`combinations()` 在衣柜有鞋且用户没有指定鞋时，为每个主体额外生成一个不含鞋的组合，打分时 `shoes.missing` −8、提醒"这套没有配鞋（衣柜里合适的鞋不多，可自选）"。于是 −25 的组合会排在不配鞋方案之后；有合适的鞋时，不配鞋方案因 −8 排在后面。组合数约增加 1/鞋数，328 件衣柜推荐耗时仍约 100 ms。

### 2.4 扣分幅度

`feature-tables.json` 的 `penalties`：

```json
"compatMild": 4, "compatSevere": 25, "weatherPerItem": 20, "weatherCap": 30, "formalitySpan3": 20,
"mixingBase": 3, "mixingLearned": 9, "idlePerItem": 1.5, "idleCap": 3, "idleDays": 30, "noShoes": 8
```

总分仍是七个维度（权重合计 100）加上规则加减，截在 0~100。`Score.severe()`：任一规则扣分 ≥10 视为"明显不合适"，这样的组合不会被选为"新尝试"，也不做闲置加分。

### 2.5 规则追踪

- **衣物级**：`Result.trace`（`GarmentTrace(id, name, role, status, rule, reason, relevance, rank, k, reasons)`），status 为 `EXCLUDED`（硬规则）、`CUT`（该位置相关度第 rank 名，只取前 k 件）、`RECALLED`；`Result.rejectedByGarment` 记录某件衣物所在组合被硬规则拒绝的第一个原因。
- **组合级**：`Score.rules`（`RuleHit(id, delta, evidence)`），只记命中的规则；解释接口按 `RuleCatalog.OUTFIT_RULES` 列出全部检查过的规则并标注命中与否。同一规则命中两次（例如一组不喜欢、一组喜欢）时解释里合并显示净分和两条依据。
- **存放**：只在运行缓存（30 分钟），不落库，不增加任何模型调用。`recommendation_log.score_vector_json` 仍记录各维度分（`penalty` 为所有扣分之和）。

`RuleCatalog` 规则表（ID / 名称 / 类别）：structure、user.excluded、user.avoid-color、user.avoid-category、sex.female-cut、image.mixing-forbid、feedback.cooldown、role.unknown（HARD）；recall.cutoff、compat.shoe-bottom、compat.shoe-occasion、compat.heels-top、sex.female-cut-guess、weather.garment、formality.span、shoes.missing、image.mixing、evidence.inferred、feedback.outfit/pair/kind/item、diversity（SOFT）；wish.style、wish.category、template、idle（BONUS）。

### 2.6 解释接口（D33）

`GET /api/recommendations/{runId}/explain?garmentId=` 或 `?outfitKey=`，只读运行缓存（他人或过期返回 410）。返回：

```json
{ "runId": "...", "intent": "通勤 · 秋季（按日期）", "status": "EXCLUDED|CUT|RANKED|SHOWN|NOT_IN_CLOSET|NOT_COMBINED|NO_VALID_OUTFIT",
  "summary": ["大白话一句或几句"], "recall": {GarmentTrace}, "bestOutfit"/"outfit": {"key","rank","of","score","garments","dimensions","rules":[{id,label,kind,hit,delta,evidence}]},
  "shownCount": 3, "lastShownScore": 82.7 }
```

判断顺序：不在衣柜 → 硬排除（说明是哪条底线）→ 召回截断（第几名、前 k 件、排在前面的是谁、可以设为必选）→ 外层/配饰（D7/D14 不进入组合）→ 没有可行组合（第一个硬规则原因）→ 已展示（第几套与总分构成）→ 未展示：分数够但与已展示方案共用主体（多样化让位），否则说明与展示最后一套的分差、扣分最多的三条规则、比最后一套少分最多的维度。

助手工具 `explain_recommendation`（`garmentId` / `outfitKey` / `query`）：始终开放的只读工具；用本会话最近一次推荐的 runId（`PreviousRecommendation` 新增 runId）；只有一句描述时用混合搜索（全部画风）定位，多件时返回 `otherCandidates`；推荐过期时用记录的意图调用 `RecommendationService.rerun`（不记推荐日志，前 count 套标为"已展示"）再解释，并告知"按同样条件重新计算"。提示词升到 platform-agent-v7，加入"问为什么没推荐时调用此工具，不要直接重新推荐"。

## 三、反馈三层、衰减、冷却（D28）与个人偏移、闲置（D32）

### 3.1 数据

不新增表。来源全部是已有表：`recommendation_feedback` + `recommendation_log`（负面与点赞）、`outfit`（保存）、`outfit_plan`（OOTD）、`wear_log`（今天穿了）、`style_signal`（OPEN_WORKSPACE、SWAP_OUT、RESTORE_ITEM、RESTORE_COMBO、新增 RESET_OFFSETS）。画像每次推荐时现算（几百条记录，毫秒级）。

### 3.2 层与键

`StyleProfile.leanings`：`O:<outfitKey>`（衣物集合，与推荐 key 同算法 `StyleProfile.outfitKey`）、`P:a|b`、`K:SHOE|LOWER`（如 `HEELS|CASUAL_PANTS`）、`I:<garmentId>`、`M:ILLUSTRATION|PHOTO`。`StyleProfileService.keys()` 由衣物 ID 列表生成一组键。

| 信号 | 正/负 | 强度 | 写入层 |
|---|---|---|---|
| 不喜欢（任意原因） | 负 | 1 | O、P、K；指定衣物时 +I；原因含"画风不统一"时 +M |
| 换一件（采用时上报） | 负 | 0.3 | 被换掉的那件与这套其余各件的 P |
| 点赞 | 正 | 1.5 | O、P、K、M，各件 I ×0.5 |
| 保存搭配 / OOTD / 今天穿了 / 在搭台打开 | 正 | 1 / 1.5 / 2 / 0.3 | 同上 |

### 3.3 衰减与倾向

`Layers`：每个键累计衰减后的正面量 P、负面量 N、负面次数、最后正面与最后负面时间。负面半衰期 30 天，正面 60 天。倾向 `t = (P − N) / max(prior=1, P + N)`。选择 max 而不是 `P + N + prior` 的原因：后者让"30 天后影响减半"无法成立（一次不喜欢 −0.5 → −0.33），而前者一次不喜欢 −1、30 天后正好 −0.5，样本少时也不会超过 ±1。

### 3.4 打分

`OutfitScorer.feedback`：整套 `14×t`；两两组合取最低 t 与最高 t 分别计 `8×t`；同类组合 `8×t`；单品取最低与最高分别 `10×t`。正面结果再乘 `positiveScale=0.3`，所有正面合计不超过 `positiveCap=+6`。负面全额。

两处取舍都来自真实账号自测：最初正面全额且取平均，结果是用户保存过的搭配一律 100 分（+32），而一次"不喜欢高跟鞋"被同套里"常选的短袖衬衫"平均抵消，只降 3 分、卡片上看不到原因。改为"负面全额、正面折算并封顶、最好和最差分开计"后，不喜欢的那件单独扣 −10 并写"你不喜欢高跟鞋"。

### 3.5 冷却期

条件：`I:` 倾向 ≤ `cooldownLeaning=−0.6`、负面量 ≥ `cooldownMass=1.2`、最后一次负面之后没有正面。冷却中的单品在召回阶段排除（规则 `feedback.cooldown`，必选除外）。预计恢复天数 = `ceil(30 × log2(N / 1.2))`（两次不喜欢约 21~23 天）。立即恢复：PATCH `/api/style-profile` `{"unblock":"pause:<id>"}` 写 RESTORE_ITEM，此前的负面不再计入 `I:` 层（整套与组合层不受影响）。屏蔽键（"不准确"）：`outfitfb:`、`pairfb:`、`combo:`、`item:`、`mix:`、`offset:warmth`、`offset:formality`、`idle:`。

**迁移**：P1.1 的"60 天内 ≥2 次暂停"没有单独存储，部署后由同一批反馈按新规则算出冷却；用户账号上那双高跟鞋部署后显示"冷却中：3 次，约 40 天后恢复"。

### 3.6 个人偏移（D32）

TOO_COLD +0.5、TOO_HOT −0.5 保暖值（上限 ±1.5）；TOO_CASUAL +0.3、TOO_FORMAL −0.3 正式程度（上限 ±1）；按负面半衰期衰减。冷暖偏移让理想保暖区间上下平移，并把温度换算为"体感"（1 保暖单位 ≈ 2°C）用于不合时宜判断；正式偏移加到场景目标正式程度（召回与场景维度都用 `OutfitScorer.target`）。清空：`{"clearOffsets":true}` 写 RESET_OFFSETS。

### 3.7 闲置激活

只有该账号存在打卡记录时才计算：每件已入柜衣物的"上次穿着"取最近一次打卡，从未穿过的取"首次打卡"与"入柜时间"中较晚者；≥30 天进入 `idleDays`。打分：这套没有 ≥10 分的扣分时，每件闲置单品 +1.5、最多 +3，标签"N 天没穿了"。

### 3.8 画像接口

GET `/api/style-profile` 新增 `cooldowns[{garmentId,name,dislikes,daysLeft}]`、`offsets`、`offsetCaps`、`feedbackHalfLifeDays`、`strictness`；`settings` 新增 `semanticStrictness`，`styleMixing` 取值 AUTO/ALLOW/FORBID（旧值 PENALTY 读作 AUTO）。PATCH 新增 `clearOffsets`、`semanticStrictness`（0~100 或 null）。

## 四、画面风格录入时得出（D29）

- **识图 schema**：`RecognitionSchema.VERSION = garment-v6`，顶层新增必填 `imageStyle`（PHOTO/ILLUSTRATION/SKETCH/OTHER），提示词 `recognition/garment-v6.txt` 在 v5 基础上加一段说明。校验时 `imageStyle` 可缺省（旧结果、回放结果仍能通过），未知值归为 OTHER。`Recognition.Result` 新增 `imageStyle`（为空不序列化），批量识别与快速入柜复制结果时保留该字段。单件识图、快速入柜、批量识图共用同一个 schema，所以三条路径都会带回画风。
- **得出顺序**（`ImageStyles.resolve`，一次查询联表 garment、image_asset、workflow_job、garment_image_style）：USER 行 → 展示图所在任务请求里的 `"imageStyle"` 参数（GENERATION）→ 识图结果的 `imageStyle`，展示图属于抠图/贴纸/忠实整理（RECOGNITION）→ 与当前展示图匹配的老判定（MODEL）→ 截止时间前、已有旧识图结果的衣物留空等待补判 → 其余由照片得到的展示图记为写实（SOURCE）。
- **一次性补判**：`app_marker` 表记录 `image-style-backfill-cutoff`（首次调用时写入当时时间）与 `image-style-backfill-done`。`ImageStyleHandler.candidates()` 在完成标记存在时直接返回；扫描到没有待补判的老衣物时写入完成标记并记日志。新衣物永远不会进入这个任务。
- **混搭学习**：见 2.4 与 3.2 的 `M:` 层。

## 五、语义搜索严格度（D30）

`Strictness.of(level, base=0.35, baseMargin=0.06)`：

| 档位 | 相似度门槛 | 中位差 |
|---|---|---|
| 0 | 0.28 | 0.04 |
| 25 | 0.315 | 0.05 |
| 50（推荐，空值） | 0.35 | 0.06 |
| 75 | 0.40 | 0.07 |
| 100 | 0.45 | 0.08 |

低于推荐档每级 −0.0014、高于每级 +0.002（实测 0.30 以下"没有"判断迅速变差，所以放宽方向更缓）；中位差每级 0.0004，最低 0.02。`SemanticIndex.strictness(owner)` 直接读 `recommend_setting.semantic_strictness`（语义包不依赖推荐包），`GarmentSearchService.search(owner, q)`、助手 `search_wardrobe`、推荐召回语义路都用它。评估（`SemanticEvaluationTest`）对 5 个档位逐一计算，并断言推荐档达标、档位越严"没有"判断越准；结果写 `target/strictness-eval.json`，存档于 `.planning/recommend-p3-20261008/strictness-eval.json`。

## 六、模板审核（D31）

- 表 `outfit_template_review(template_id, review_status PENDING_REVIEW|APPROVED|REJECTED, enabled, bonus, updated_by, updated_at_ms)`；没有行即用资源文件默认值，资源文件不被改写。
- `OutfitTemplates` 现在保留全部条目（`Entry`：状态、启用、当前与默认加分、审核人、原始条件）；`withReviews()` 叠加数据库状态；只有 APPROVED 且启用的进入打分。
- `TemplateCatalog`（单例）缓存当前模板集，每次审核后重新加载；`RecommendationService.engine()` 发现模板集变化就重建引擎，因此立即生效。采用（adopt）等路径也走同一个引擎。
- 接口（`/api/admin/**` 仅管理员）：GET `/api/admin/outfit-templates`；PATCH `/api/admin/outfit-templates/{id}` `{reviewStatus?, enabled?, bonus?}`（加分 0~5，按 0.5 取整）；POST `/api/admin/outfit-templates/review` `{ids, reviewStatus}`（1~200 条）。
- 本期不做演示衣柜上的命中预览（可选项）；按 AGENTS.md 的可插拔约束，没有放进 `/api/manage/v1`。

## 七、前端（smart-closet）

组件清单与入口见总设计第八节。实现要点：

- **复用**：`RecommendationGroup`（卡片组 + 详情 + 换一批）在组合台推荐区、助手快捷入口、指代选择卡、聊天卡片"修改条件重算"四处共用；聊天里原有的 `RECOMMENDATION` 大模态框新增按钮打开同一个 `RecommendationDetailModal`。
- **预览场景**：`sceneCache.outfitScene` 复用 `bridge.candidateScene` 的自动布局，按衣物集合缓存，避免卡片与详情重复取图。
- **在搭台打开**：`workspace.openInWorkspace` 写本机草稿（与助手"新建草稿"相同的键格式）并跳转 `/outfits/new?draft=…&from=recommend&run=…&key=…`，编辑页据此显示来源提示与"查看依据"。
- **今天穿了**：推荐详情直接按衣物打卡；已保存搭配与编辑页按 outfitId 打卡；`GET /api/wear-logs/outfits` 给出每套最近穿着日期，`GET /api/wear-logs/garments/{id}` 给出单件次数与上次日期。
- **行为事件**：`recommendApi.signal` 读取画像开关（`profile()`/`updateProfile()` 更新），关闭后直接丢弃；VIEW_DETAIL 每套每次打开一次，OPEN_WORKSPACE 在打开草稿时，SWAP_OUT 在采用替代品时。
- **意图回显**：后端在聊天推荐载荷中新增 `intentInput`（场景、温度、风格、颜色、品类、描述、必选、数量），前端意图条预填，修改后直接调用推荐接口。
- **选择卡**：后端 `search_wardrobe` 命中多件且是第一页时创建 `GARMENT_CHOICE` 提议（前 4 件），运行时把它作为 proposal 事件发给前端、对模型只说"选择卡已展示"；点击后 `requiredGarmentIds=[id]` 推荐。
- **组件注册**：项目按需注册 Ant Design Vue 组件，本期新增 `a-table`、`a-popconfirm`、`a-skeleton-image`（漏注册会静默不渲染，自测时发现）。
- **服务端路由**：`ClosetSpaController` 增加 `/admin/templates`，否则直接打开该地址会 404。

## 十、已知局限

- 规则追踪只在 30 分钟缓存里；过期后由助手按同样条件重算解释，结果可能与当时略有不同（已在回复中说明）。
- 助手快捷入口的结果只显示在当前聊天、不进对话记录，因此刷新后消失，也不能用"沿用上一轮"接着改。
- 组合台推荐区"今天穿了这套"不要求先保存为搭配（总设计 8.3 原写"会提示先保存"），打卡按衣物集合记录。
- 模板审核没有做演示衣柜命中预览；模板库仍全部为待审核，需要用户审核。
- 冷却期估算只按负面衰减计算，不考虑之后可能出现的正面信号（出现正面会立即结束冷却，不影响正确性）。
