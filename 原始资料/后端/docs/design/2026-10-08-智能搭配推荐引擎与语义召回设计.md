## 一、目标与非目标

### 目标

1. **消除低级错误**：撞色、季节不对、冷热不对、正式程度不搭、理由与衣物不符、总推同几件。
2. **白盒可解释**：每套推荐、每件单品都能说清"为什么在这里"，依据来自后端计算，不是模型自由发挥。
3. **控制成本**：能用代码算的不调大模型；必须调用时只调一次，输入尽量少；结果可缓存的就缓存。
4. **语义召回**：理解"海边度假""那件小熊卫衣"这类字段覆盖不到的说法；同一套能力开放给衣柜搜索。
5. **可回归**：用固定测试衣柜和"坏搭配"断言保证以后改规则不会退化。

### 非目标（本期不做）

- 不训练个性化推荐模型（用户量与数据量都不支持，规则加反馈权重已经够用）。
- 不引入向量数据库（单个衣柜规模在几百件，内存计算足够）。
- 不改变现有叠穿安全规则的底线（见决策 D7）。
- 不做购物推荐，不联网检索穿搭资讯。

## 二、成本与诚实原则（贯穿全文）

| 原则 | 具体含义 |
|---|---|
| 能算的不调模型 | 召回、组合、打分、多样化、理由模板、理由核对、取色、语义向量全部本地完成 |
| 必须调用时只调一次 | 聊天推荐压缩为"一次决策调用 + 一次回复调用" |
| 输入要少 | 工具结果只给模型 3~5 套推荐的要点，不再给 40 套候选和全部衣物资料 |
| 缓存 | 推荐结果按"衣柜版本 + 意图"缓存，"换一批"和"换一件"直接取已算好的结果 |
| 付费能力需要用户主动开启 | 多模态复核默认关闭，开启后计入额度，结果按衣物组合缓存 |
| 没有就说没有 | 召回结果为零时如实返回，并给出"最接近的是……"，不悄悄替换 |
| 推测不当确认 | 识图推测的字段（INFERRED）只参与扣分，不作为硬排除依据，并在界面标注 |

## 五、模块设计

### 5.1 结构化意图 Intent

推荐的全部输入都收敛为一个对象，来源有三种：页面控件、词典解析、模型填写的工具参数。

```json
{
  "occasion": "COMMUTE",            // 场景，见下表，可空
  "temperatureC": 12,               // 用户说的或天气接口给的，可空
  "season": "秋",                   // 温度缺失时按日期推断，标注 source
  "formality": null,                // 1~5，可空，空时取场景默认值
  "wantStyles": ["简约"],
  "wantColors": [], "avoidColors": ["亮色"],
  "freeText": "看起来文艺一点",       // 字段对不上的剩余描述，交给语义召回
  "requiredGarmentIds": [],
  "excludedGarmentIds": [],
  "count": 3,
  "sources": {"temperatureC": "USER", "season": "DATE"}
}
```

- **场景枚举**：日常 DAILY、通勤 COMMUTE、约会 DATE、运动 SPORT、户外 OUTDOOR、正式 FORMAL、度假 TRAVEL、居家 HOME。每个场景带默认正式程度和各打分维度的权重。
- **词典解析**：颜色、品类、季节、风格词表直接取 `RecognitionSchema.FIELDS` 里的选项，另加一份小同义词表（如"浅色"→白/米/灰，"亮色"→红/橙/黄/粉，"冷"→温度下调）。页面搜索与推荐共用。
- **透明**：意图会原样返回并展示在推荐卡片顶部（例如"通勤 · 12°C（你说的）· 避开亮色"），理解错了一眼就能看出来，点一下就能改。

### 5.2 衣物特征层 GarmentFeatures

每件衣物派生出一份打分用的特征，按 `garment.id + revision` 缓存在内存里（衣物修改后 revision 变化，缓存自然失效）。

| 特征 | 来源 | 说明 |
|---|---|---|
| role | 现有 `OutfitRules.role` | 穿着位置 |
| warmth 保暖值 0~5 | 品类基准 + 厚薄 + 袖长 | 例如羽绒服 5、大衣 4、毛衣 3、长袖衬衫 2、T 恤 1、短裤 0.5 |
| formality 正式程度 1~5 | 品类基准与风格标签取平均 | 运动 1、休闲 2、通勤 3~4、正式 5；西装外套 4、运动鞋 1.5 |
| colors | 主色 + 辅色（P4 后加精确色值） | 区分中性色和强调色 |
| patternStrength | 花纹 | 纯色 0；条纹/格纹/波点 1；花卉/图形印花/迷彩/动物纹/拼色 2 |
| seasons / styles | 现有字段 | |
| confidence | 每个字段的 `quality.status` | USER_CONFIRMED > OBSERVED > INFERRED > UNKNOWN |

各基准值放在 `src/main/resources/recommend/feature-tables.yml`，带版本号，测试与线上共用。

### 5.3 单品召回（按穿着位置）

对每个穿着位置（上装、下装、连体、鞋，可选外层和配饰）分别打"相关度分"，每个位置保留前 K 件。

**相关度 = 字段匹配 + 关键词 + 语义相似度**（三路加权合并）：

| 路 | 做什么 | 示例 |
|---|---|---|
| 字段匹配（主力） | 季节、冷暖、风格、颜色是否符合意图；不符合的硬性条件直接排除 | 意图"避开亮色" → 红色上衣排除 |
| 关键词 | 名称、可见文字、品牌命中加分 | "优衣库" |
| 语义 | `freeText` 与衣物描述卡的向量相似度（见 5.9） | "海边" ≈ 亚麻、浅色、短袖 |

- 默认 K：上装 15、下装 10、连体 8、鞋 6、外层 5、配饰 4，可配置。组合规模约为 15×10×6≈900 套，与衣柜总量无关。
- 必选衣物直接进入对应位置，不参与截断。
- 每件被召回的单品记录命中原因，例如 `["季节=秋 ✓", "风格=通勤 ✓", "语义'文艺' 0.78"]`。
- 某个位置为空时（例如没有鞋），流程继续，不凑数，并在结果中说明"没有符合条件的鞋"。

### 5.4 组合与约束

在召回结果上做组合，先过底线硬规则，再打分。**2026-10-09 起（D27）只有底线规则排除，其余一律加权扣分**，见 5.4.1。

- **结构约束（硬）**：完整复用 `OutfitRules.validate`，叠穿安全底线不变。
- **冷暖（扣分）**：只在温度来源为用户或天气接口时启用。温度分档：炎热 ≥28、温暖 22~28、舒适 15~22、微凉 8~15、寒冷 <8，各档有保暖值区间，超出区间降低冷暖维度分；明显不合时宜的单品（10°C 穿短裤、30°C 穿羽绒服）每件 −20，合计最多 −30。个人冷暖偏移（D32）会平移温度档。
- **正式程度（扣分）**：同一套正式程度最高与最低之差 ≥3 时 −20，差 2 时降低风格维度分。

### 5.4.1 底线硬规则 + 加权扣分表（P1.1 建立，P3 收敛，D27）

用户要求：除底线外都由引擎打分判断，避免以后出现难以排查的组合问题。每次推荐都记录每件衣物、每套组合经过的规则（规则 ID、命中与否、加减分、依据），可以用解释接口和助手工具 `explain_recommendation` 查询（D33）。规则目录在 `RuleCatalog`，扣分幅度在 `feature-tables.json` 的 `penalties` 与 `feedback`。

**底线硬规则（只有这三类会排除）**

| 规则 ID | 内容 | 依据 |
|---|---|---|
| `structure` | 重复穿着位置、缺少主体（`OutfitRules`） | 结构不可能 |
| `user.excluded` / `user.avoid-color` / `user.avoid-category` / `feedback.cooldown` / `image.mixing-forbid` | 本次指定排除的衣物、本次要避开的颜色、记忆中"不穿 X"、冷却中的单品（多次明确"不喜欢"）、画风混搭设为"总是不混" | 用户明确表达 |
| `sex.female-cut` | 性别为男时自动推荐不使用女款（品类为推测时降为扣分 `sex.female-cut-guess`；用户指定的必选衣物除外） | 性别底线 |

`role.unknown`（品类不明，无法判断穿着位置）不参与组合，并在 limits 里提示补全。

**加权扣分表（总分 100 制，依据文字照常显示在卡片提醒里）**

| 规则 ID | 触发 | 扣分 |
|---|---|---|
| `compat.shoe-bottom` / `compat.shoe-occasion` / `compat.heels-top` | 兼容表一般不合适（PENALTY） | −4，风格维度另减 0.35 |

| `weather.garment` | 温度明显不合时宜的单品 | 每件 −20，合计最多 −30 |
| `formality.span` | 正式程度跨度 ≥3 | −20 |
| `material.double-denim` | 主体里两件及以上牛仔（品类含"牛仔"或纹理为牛仔纹理），如牛仔衬衫配牛仔裤（2026-10-09 内测修复）；全部是用户指定时不扣 | −8 |

| `feedback.outfit` / `feedback.pair` / `feedback.kind` / `feedback.item` | 反馈三层与单品（5.11） | 倾向 × 14 / 8 / 8 / 10；正面折算 0.3、合计最多 +6 |

### 5.4.2 展示图画面风格（2026-10-08 补充，P3 改为录入时得出，D29）

衣柜展示图大多是写实实物，也有卡通插画、简笔线稿，以后还可能整体卡通化。画面风格属于"展示图"的元信息，**在录入时得出，不另外计费**。

| 值 | 含义 |
|---|---|
| PHOTO 写实实物 | 实物照片、抠图或逼真的商品渲染图 |
| ILLUSTRATION 卡通插画 | 卡通、插画、动漫、平涂色块或明显描边 |
| SKETCH 简笔线稿 | 以线条为主的简笔画、线稿、手绘草图 |
| OTHER 其他 | 看不清、不是衣物或无法判断 |

**来源（按顺序取第一个，全部零额外调用，`ImageStyles.resolve`）**

1. 用户手动设置（PUT `/api/garments/{id}/image-style`），永不被覆盖。
2. 生成参数指定：展示图所在任务的请求参数里带 `imageStyle`（以后整体卡通化时写入）。
3. 识图结果：识图 schema 升级为 `garment-v6`，同一次识图顺带输出 `imageStyle`；展示图是这张原图的抠图、贴纸或忠实整理（AI 增强的提示词只做"整理/忠实提取"，不改变画风）时采用。
4. 老数据的一次性网格判定（`IMAGE_STYLE`，见下）。
5. 按来源推断：由用户照片抠图或整理而来的展示图为写实。

**实测修正**：用户衣柜里有 2 件贴纸展示图被判为卡通——上传的就是卡通图，抠图后仍是卡通。所以"抠图一律写实"只作为最后的兜底，优先用同一次识图对原图的判断。

**老数据补判**：`IMAGE_STYLE` 网格任务（最多 12 张拼一张图，1 次识图额度）只处理截止时间（首次运行时记录在 `app_marker`）之前录入、识图结果里没有画面风格、也没有判定记录的衣物；扫描到没有剩余时写入完成标记，此后不再自动扫描。新录入的衣物不会进入该任务。用户衣柜 48 件在 P2 时已判定，P3 部署后首次扫描即标记完成。

- **推荐**：同一套出现两种以上已知风格（OTHER 和未判定不算）时，按设置处理：AUTO（默认，自动学习）扣分并写"单品图片风格不一致（写实实物与卡通插画）"，默认 −3，用户保存、穿着、点赞过同样的混搭则扣分逐渐减小到 0，以"画风不统一"（`STYLE_MISMATCH`）点不喜欢则加大到最多 −12；ALLOW 不处理；FORBID 排除（用户明确设置，属于底线）。旧值 PENALTY 视为 AUTO。
- **搜索**：默认只看衣柜中数量最多的风格（未判定的保留），被隐藏的命中提示"另有 N 件其他风格"；说"卡通/简笔/写实/全部风格"或传 `imageStyle` 可切换。
- **接口**：GET `/api/garments/image-styles` 查看分布与来源（USER / GENERATION / RECOGNITION / MODEL / SOURCE）。

### 5.4.3 风格词理解（2026-10-08 补充）

用户说的风格词千变万化（可爱、千金风、多巴胺、老钱……），衣柜里的风格标签只有一套词汇（休闲、运动、通勤、正式、复古、甜美、户外）。按以下顺序把一个词归到标准风格：

1. **词表**（`feature-tables.json` 的 `styleSynonyms`）：人工维护的精确映射，包含匹配（"可爱风""超可爱"都算）。
2. **已学会的词**（V18 `style_term`）：聊天时大模型本来就要理解这句话，`recommend_outfits` 的参数里顺带给出 `styleTags`（只能从标准风格中选）。这一判断当场用于推荐，并在只有一个新词时记入词库；之后衣柜搜索、一键推荐等不经过大模型的入口也能直接用。**不增加任何模型调用。**词库可查看（GET `/api/style-terms`），管理员可停用某个词。
3. **本地近邻**：与每个风格的十来个示例词比较，只在领先明显时采用（领先所有风格平均值 ≥ 0.14）。实测本地小模型懂具体词（瑜伽、晚宴、面试），不懂时尚黑话（多巴胺、美拉德），所以宁可不判。
4. 仍判断不了的词作为描述交给衣物层面的语义匹配。

衣物上的自定义风格标签（洛丽塔、学院风、千金风……）按同样的顺序归到标准风格。每次推荐的意图回显会写出依据，例如"想要千金风（≈甜美/正式（助手判断））"。

用户明确提出的风格和单品类型（`wantCategories`）在总分上单独加减（满足最多 +6、完全不符 −6），不受维度分封顶影响，满足时作为第一条亮点。

### 5.5 组合打分

总分 0~100，由各维度加权求和；权重随场景变化（例如运动场景提高冷暖权重、降低色彩权重）。**每个维度都必须输出"得分 + 依据文字"**，依据会直接展示给用户。

| 维度 | 默认权重 | 规则要点 |
|---|---|---|
| 色彩 | 25 | 见下文色彩规则；命中搭配模板库（5.16）时加分 |
| 冷暖 | 20 | 保暖值与温度档的贴合度；只有日期推断的季节时只看季节标签 |
| 风格一致 | 15 | 各件风格标签的重合度 + 正式程度跨度 |
| 场景贴合 | 15 | 正式程度与场景默认值的距离 + 场景风格词命中 |
| 召回相关度 | 10 | 各单品召回分的平均（保证"海边"这类需求不会在组合阶段丢失） |
| 个人偏好 | 10 | 穿搭画像（见 5.15）：记忆中的喜好/避开项、反馈、收藏、已保存搭配、固定组合 |
| 新鲜度 | 5 | 近 7 天推荐或保存过的单品扣分 |
| 资料可信度 | 不加分，只扣分 | 关键字段是推测或缺失时扣分，并在卡片上标"⚠ 厚度为推测" |

**色彩规则（第一版用色名，P4 接入精确色值后升级）：**

- 中性色：黑、白、灰、米、棕、藏蓝；牛仔蓝视为中性。
- 强调色数量：不超过"配色胆量"允许的数量（保守 1 / 适中 2 / 大胆 3，见决策 D9）。
- 冲突色对扣分：红-绿、紫-黄、橙-紫、红-粉（大面积时）等，列表放在配置文件里。
- 同色系或全中性色加分（统一感）。
- 花纹：一套里最多一件强花纹（patternStrength=2），两件强花纹扣大分；条纹配格纹扣分。
- 鞋与包颜色呼应主体颜色时加分。

### 5.6 多样化挑选

按分数从高到低贪心挑选：每挑中一套，与它共用上装/下装/连体的其余组合降分（共用一件降 30%，共用两件降 70%）。这样三套推荐尽量换主体，不会只换双鞋就算一套。主体不够时如实标注"同一主体的配件变化"。

结果整体缓存 30 分钟：缓存键为"衣柜版本号 + 意图哈希"，"换一批"直接取后续名次。

### 5.7 理由：模板生成 + 核对

- **模板理由（零模型）**：由打分依据拼出，例如"藏蓝+白，经典配色 · 三件都偏通勤 · 保暖值适合 12°C"。页面入口直接使用模板理由。
- **聊天理由**：模型可以改写成更自然的话，但回复提交前，后端用词典扫描理由里出现的颜色词、品类词，凡是不属于该套衣物的，退回让模型修改一次；仍不通过就改用模板理由。这一步不需要额外模型调用。

### 5.8 Agent 改造

**新工具 `recommend_outfits`**：替代"`get_outfit_candidates` → 模型挑选 → `build_outfits`"三步。

```
参数：intent（5.1 的结构）, open: "CARDS" | "WORKSPACE"
返回给模型（精简）：
  intent（回显）
  outfits: [{rank, outfitKey, items:[{name, role, color}], score, highlights:[3 条], warnings:[]}] × 3~5
  emptyReason / limits（例如"没有符合条件的鞋"）
```

- 模型不再接触 40 套候选和全部衣物资料，预计单次推荐输入 token 下降一个数量级（以决策追踪中的实测数据为准，P1 验收时给出前后对比）。
- 模型选择自由度见决策 D11。
- `get_outfit_candidates` 保留一个版本周期，用于需要手工微调的场景，之后下线。
- ~~`AgentIntentPolicy` 的正则门控不变：只有识别到搭配意图时才开放该工具。~~ **2026-10-08 调整**：`recommend_outfits`、`present_outfits` 只计算并展示卡片，不写任何数据（打开到画板、保存都要用户点击），改为始终开放，由模型按对话判断；用户实测多次因说法没被正则识别而拿不到推荐。直接打开到画板（`open=WORKSPACE`）仍需本轮识别到搭配意图，否则只出卡片。
- 系统提示词中关于"如何挑选候选"的大段说明删除，改为"使用 recommend_outfits，按返回的 highlights 解释，不编造颜色"，提示词变短也省 token。

### 5.9 语义索引（本地，零 API 费用）

**描述卡**：每件衣物生成一段文字，例如：

```
藏蓝色 圆领 长袖 针织衫；纯色；合体；常规厚度；休闲 通勤；春 秋；
名称：小熊毛衣；可见文字：BEAR；识图描述：胸前有小熊刺绣
```

**向量模型**（决策 D1、D2）：

- 推荐 `bge-small-zh-v1.5` 的 ONNX 版本，约 100MB，512 维，中文效果好。
- 复用现有 `onnxruntime` 依赖与 `U2NetEngine` 的加载模式；分词器（WordPiece）用 Java 实现，读取模型自带的词表。
- 单条推理时间待在部署机器上实测，验收标准：几百件衣物全量补算在 1 分钟内完成，单次查询编码 <100ms。

**存储与更新**：

- 新表 `garment_embedding(garment_id, owner_username, model_version, card_hash, vector BLOB, updated_at_ms)`。
- 衣物入库、识图完成、元信息修改后，在现有持久任务队列里排一个本地计算任务；`card_hash` 未变就跳过。
- 换模型时 `model_version` 变化，后台按用户分批重算；重算完成前该用户的语义召回自动降级为字段加关键词，不报错。
- 启动时不全量加载；查询时按用户读取该用户的向量（几百条 × 512 维 ≈ 1MB），短期缓存。

**查询**：

- 余弦相似度，低于门槛的不返回（门槛先定 0.5，用测试集调整）。**P2 实测**：单一门槛无法区分真命中与"没有"，改为"相似度 ≥ 0.35、高出该查询中位相似度 ≥ 0.06、不低于最佳 0.12 以上"，衣柜外品类名词走字段判定；评估数据见 P2 报告。
- 硬性条件（颜色、品类）一律走字段筛选，语义只负责字段覆盖不到的描述。这样可以避免"问红色返回粉色"。

### 5.11 反馈：三层、衰减、可反悔（P3 重写，D28）

- 表 `recommendation_log`（每次展示的推荐与当时各维度得分）、`recommendation_feedback`（UP/DOWN + 原因：颜色不搭、太热、太冷、太正式、太随意、不喜欢某一件、画风不统一、很喜欢）、`style_signal`（打开详情、在搭台打开、换一件、恢复与清空）不变。
- **一次"不喜欢"写到三层**，由强到弱：整套（`O:` 所含衣物集合）、两两衣物组合（`P:`，尤其鞋与下装、上装与下装）、同类组合（`K:` 鞋款类型 × 下装类型，例如高跟鞋 × 休闲长裤，能泛化到另一双同类鞋）；指定了不喜欢某一件时同时写入单品层（`I:`）。"画风不统一"另写图片风格混搭层（`M:`）。
- **正面信号**：点赞 1.5、保存搭配 1、OOTD 1.5、今天穿了 2、在搭台打开 0.3，写入同样的层（单品层按一半）。换一件只对"被换掉的那件 × 这套其余衣物"的组合层记 0.3 的负面，不当作讨厌这件。
- **衰减**：负面半衰期 30 天，正面 60 天（`feature-tables.json` 的 `feedback`）。
- **正负抵消**：每层倾向 = (正面 − 负面) / max(1, 正面 + 负面)，取值 −1~1。一次不喜欢即 −1，30 天后影响正好减半；之后喜欢了自然回正。进入打分时负面全额（权重 14/8/8/10），正面折算 0.3 且合计不超过 +6；组合层与单品层分别取最不喜欢、最喜欢的一项计分，不做平均（避免喜欢的衬衫抵消不喜欢的鞋）。
- **冷却期替代永久暂停**：单品倾向 ≤ −0.6、剩余负面量 ≥ 1.2（约两次不喜欢）、且最后一次负面之后没有任何正面信号时冷却，召回阶段排除（必选除外）；画像显示"冷却中，预计约 X 天后恢复"（按负面量衰减到门槛的天数估算），可立即恢复（写 RESTORE_ITEM，之前的负面不再计入单品层）。衰减到门槛以上或出现正面信号自动恢复。P1.1 的永久暂停没有单独存储，全部由同一批反馈按新规则重新计算，部署即迁移。
- **个人冷暖与正式程度偏移（D32）**：太冷 +0.5 保暖值、太热 −0.5（上限 ±1.5，换算为温度档平移约 2°C/单位）；太随意 +0.3、太正式 −0.3 正式程度（上限 ±1）。同样按负面半衰期衰减，画像可见、可清空（写 RESET_OFFSETS，之后重新统计）。
- 反馈只进入穿搭画像，不写入长期记忆（D12）。新鲜度见 D6。

### 5.12 天气（P4，已实施，D36）

- `OpenMeteoWeather`：Open-Meteo（免费、无需密钥），只发送设置页"常住城市"的名字；需要在部署机器放行 `geocoding-api.open-meteo.com` 与 `api.open-meteo.com`。
- 城市来源见决策 D5。用户填了温度就不查天气；代表温度 = 0.6×最高 + 0.4×最低；季节随温度（用户指定季节时不改）。
- 预报缓存 1 小时，城市坐标进程内缓存，失败缓存 10 分钟；任何失败降级为日期推断季节，卡片照常标注。页面推荐、助手推荐、今日灵感共用。

### 5.13 精确取色（P4，已实施，D37）

- 对展示图（透明 PNG）在 CIELAB 空间做 k=3 的 k-means（纯 Java，未引入 OpenCV；跳过透明像素），记录 L/a/b 与面积占比，结果绑定当时的展示图，换图即重算。
- 后台任务 `COLOR_INDEX` 补算全部衣物，零模型费用。
- 实测规则只在整套每件都已测色时生效：明度层次、高饱和互补对比过强、同色系和谐、识图说彩色但实测低饱和按中性色处理。细节见 P4 实现设计第五节。

### 5.14 多模态复核（原 P5，已移入后续池，未实施）

- 对排名前 3~5 套生成拼图（复用现有画板渲染），交给有视觉能力的模型，**使用固定评分表**，要求输出 JSON：`{colorHarmony 1-5, proportion 1-5, styleCoherence 1-5, issues[]}`。
- 结果只用于重新排序和提示，硬约束仍以后端为准。
- 按"衣物 ID 组合 + revision"缓存，同一组合不重复付费。
- 额度归属见决策 D16。

### 5.15 用户穿搭画像（行为数据）

**目标**：让推荐越用越懂这个人，同时保证"懂"的依据用户自己看得见、改得了。全部用统计计算，零模型费用。

**信号来源**（按可信程度从高到低，权重随之递减）：

| 层级 | 信号 | 现有数据 | 权重 |
|---|---|---|---|
| 明确表达 | 长期记忆里明确说出的偏好（"喜欢藏蓝""不穿紧身"） | `agent_memory_document` | 最高，硬偏好可直接作为过滤条件 |
| 明确表达 | 推荐反馈 👍/👎 + 原因 | 新增 `recommendation_feedback` | 高 |
| 明确表达 | 收藏的衣物 | `garment.favorite` | 中高 |
| 强行为 | 保存的搭配（尤其是反复修改、保存多次的） | `outfit` | 高 |
| 强行为 | 用某套搭配生成了 OOTD | `outfit_plan` / `image_render_job` | 高 |
| 强行为 | "今天穿了这套"打卡（D6） | 新增 | 最高的行为信号 |
| 弱行为 | 推荐卡片"在搭台打开" | 新增埋点 | 低，正向 |
| 弱行为 | "换一件"时被换掉的单品 | 新增埋点 | 低，负向（只针对这次的组合，不是讨厌这件） |
| 弱行为 | 助手提议被接受或忽略 | `agent_proposal.consumed` | 低 |

**画像内容**（都是属性层面的统计，每一项带依据数量）：

- **颜色偏好**：常穿颜色、常用颜色组合。例如"保存的 12 套里有 8 套含藏蓝"。
- **品类与风格偏好**：例如更常穿半身裙还是长裤，通勤风占比多少。
- **正式程度习惯**：平时搭配的正式程度分布，作为"日常"场景的默认值。
- **单品亲和度**：哪些衣服常被选、哪些从不被选（闲置）。
- **固定组合**：哪件上装经常配哪条下装（从已保存搭配里统计共同出现次数）。用途有两个：组合打分加分（"你常这样穿"），以及推荐卡片上提示"这是你的经典组合"。

**计算方式**：

- 每个信号带时间衰减（行为半衰期 60 天；反馈三层中负面 30 天、正面 60 天，见 5.11），旧习惯会慢慢淡出。
- 按季节分开统计：夏天的偏好不影响冬天。
- **证据门槛**：同一项偏好至少有 3 条独立信号才生效，避免"保存过一次红色就以为你喜欢红色"。
- 平滑处理：样本少时向默认值靠拢，样本越多越相信个人数据。
- 增量更新：每次产生新信号时更新该用户的画像，存进 `user_style_profile`，推荐时直接读取。

**进入打分**：画像体现在"个人偏好"维度里（5.5），依据文字直接引用统计，例如"偏好 +8：你保存的搭配中 70% 是通勤风"。偏好是加分项，不做硬排除；只有记忆里明确说"不穿"的才排除。

**避免越推越窄（信息茧房）**：见决策 D20。推荐的 3 套里固定留 1 套作为"新尝试"，从低频但合规的单品或颜色组合中挑，卡片上明确标注；这一套的反馈对画像的影响也更大。

**闲置激活（P3 已实施，D32）**：用户有"今天穿了"打卡记录时，30 天以上没穿的衣物（从未穿过的按"首次打卡与入柜时间较晚者"起算）在这套没有重扣分（单条 ≥10 分）的前提下每件 +1.5、最多 +3，卡片标签"N 天没穿了"，画像列出最久没穿的 5 件。没有任何打卡记录时不加分也不显示。

**透明与控制**：设置页新增"我的穿搭画像"：

- 用大白话列出每一项偏好和依据，例如"你偏爱藏蓝（依据：8 套搭配、3 次👍）"。
- 每一项都可以点"不准确"删除或屏蔽，也可以一键清空、重新开始。
- 可以整体关闭"根据我的行为调整推荐"（关闭后前端也不再上报行为事件）。
- 冷却中的单品显示预计恢复天数并可立即恢复；个人冷暖与正式程度偏移可清空（P3）。

**冷启动**：没有数据时使用默认权重；可选一个 30 秒的引导（选几张喜欢的风格图或颜色），之后完全靠行为积累。

### 5.16 用户以外的数据源

按"价值 / 成本 / 风险"排序，结论在每项最后：

| 数据源 | 能带来什么 | 成本与风险 | 结论 |
|---|---|---|---|
| **搭配模板库**（经典组合规则，例如"白 T + 牛仔裤 + 小白鞋""同色系叠穿""上宽下窄"） | 给打分提供"经过验证的好搭法"，命中模板加分并作为理由 | 一次性整理成 YAML，版本化；可以用大模型**一次性**生成初稿再人工审核，费用只花一次 | **推荐，P1 做第一版** |
| **色彩搭配知识**（色相环、经典配色表） | 色彩打分更专业 | 写进规则和配置，零运行成本 | **推荐，已含在 5.5，P4 升级** |
| **天气** | 冷暖判断 | 免费接口，需放行域名 | 已在 5.12 |
| **日历与场合**（用户主动填写"明天面试"或接入日历） | 自动带出场景 | 接日历涉及授权和隐私 | 先只做手动填写，日历以后再说 |
| **平台内跨用户的聚合统计**（例如"很多人把藏蓝配卡其"） | 冷启动时有参考，能发现大众认可的搭法 | 衣服是每个人独有的，只能做到**属性层面**的统计；需要用户量足够大；涉及隐私，必须匿名、可退出，并设最少人数门槛 | **暂不做**，见 D21 |
| **公开学术数据集**（Polyvore、iFashion 等） | 可以离线训练"搭配兼容度"模型 | 许可证多数限研究用途；国外数据与用户实际衣柜差距大；需要引入训练流程 | **不做** |
| **流行趋势**（时尚资讯、电商热销） | 推荐更"潮" | 需要联网抓取，时效性和可靠性都难保证，偏离"用自己的衣服"这个核心 | **不做** |
| **大模型自身的穿搭常识** | 本来就有 | 每次调用都花钱 | 只通过"一次性生成模板库"的方式利用，不在每次推荐时调用 |

### 5.17 推荐算法路线：纯计算为主，大模型只做"嘴"和"耳朵"

本设计本身就是业界常见的混合推荐结构，只是每一层都按个人衣柜的数据规模选了最合适的算法：

| 环节 | 业界叫法 | 本设计的做法 | 用不用大模型 |
|---|---|---|---|
| 听懂需求 | 查询理解 | 词典解析；聊天中由模型填写意图参数 | 仅聊天时用 |
| 挑单品 | 召回 | 字段筛选 + 关键词 + 本地语义向量（5.3、5.9） | 否 |
| 组合与打分 | 精排 | 规则 + 基于内容的打分 + 穿搭画像（5.5、5.15） | 否 |
| 去重、探索 | 重排 | 多样化 + "新尝试"位（5.6、D20） | 否 |
| 说给用户听 | 解释 | 模板理由；聊天时模型改写，后端核对（5.7） | 仅聊天时用 |

**结论：推荐引擎本身不需要大模型。** 页面入口全程零模型调用；大模型只在聊天里负责理解自然语言和组织回复。

**为什么不直接上"大数据推荐算法"**：

- **协同过滤**（"买了这个的人也买了那个"）依赖大量用户共享同一批商品，而每个人的衣服都是独有的，经典做法用不上。可以变通的是"你自己的衣服之间谁常和谁一起穿"，也就是 5.15 的固定组合；跨用户只能做到属性层面，需要用户量支撑（D21）。
- **深度搭配兼容模型**（用海量穿搭图片训练"这几件搭不搭"）需要大规模标注数据和训练、推理设施，现阶段投入产出不成正比。
- 这类算法的前提是"大数据"。在数据量小的阶段，规则加内容匹配反而更准、更可解释，冷启动也没问题。

**按数据量逐步升级（每一步都是纯计算）**：

| 阶段 | 触发条件 | 做法 | 说明 |
|---|---|---|---|
| ① 规则 + 内容匹配 | 现在 | 本设计 P1~P3 | 权重由人工设定 |
| ② 学习权重 | 某用户累计约 50 条以上反馈或打卡，或全平台累计数千条 | 用逻辑回归之类的简单模型，根据"当时各维度得分 → 用户是否喜欢"学出每个人的权重；Java 直接实现，不引入新组件 | 仍然可解释：学到的权重本身就是"你更在意颜色还是舒适度"，画像页可以展示 |
| ③ 探索与利用 | 与 ② 同时 | "新尝试"位从固定比例改为多臂老虎机（Thompson 采样）：哪类尝试常被喜欢，就多推这一类 | 纯统计 |
| ④ 跨用户 | 活跃用户达到一定规模（D21） | 属性层面的匿名聚合，给冷启动用户做参考 | 隐私前置 |
| 不做 | — | 深度兼容模型、大模型逐套打分 | 成本高、黑箱 |

为让 ② 将来能够直接落地，P1 起 `recommendation_log` 就记录每套推荐的各维度得分（score_vector）和规则版本。

### 5.18 成本与效果统计（P4，已实施，D39）

- `GET /api/recommendations/stats?days=` 同时给出效果（推荐套数、采用率、好评率、在搭台打开、3 天内穿了、换一件、按来源拆分）与成本（助手消息、识图/生图额度、助手 token、零模型推荐套数）。
- 助手每轮结束把上游报告的 token 写入 `model_usage`（只记数字）。设置页"穿搭画像"底部可看近 7/30/90 天；本期不进可插拔管理接口。
- P1 验收时给出改造前后同一批测试请求的 token 对比。

### 5.19 模板库扩展与流行（P4，已实施，D34）

- 模板新增适用人群、季节、场合、类型（经典/流行）、有效期与出处；槽位新增版型与最少花纹。
- 流行模板由人整理、管理员审核，过有效期自动失效；命中显示"流行搭法：…"并加"流行"标签。不联网抓取流行趋势。

### 5.20 今日灵感（P4，已实施，D35）

- 以已审核的搭法为骨架，用用户自己的衣服填充，再用同一套白盒打分挑最好的组合；每天轮换，7 天内用过的搭法靠后。
- 恰好差一件的搭法给出"差 X 就能穿……"，只描述条件，不做购物推荐。

### 5.21 语义模型的接入、重载与首次建索引（部署补充，D41）

**文件与路径**：向量模型 `embedding-fp32.onnx` 与词表 `embedding-vocab.txt`、抠图模型 `u2net.onnx` 都放宿主机 `./models`，容器挂载为 `/models`。Dockerfile 与 compose 显式设置 `CLOSET_EMBEDDING_MODEL_PATH`、`CLOSET_EMBEDDING_VOCAB_PATH` 指向 `/models`（此前默认值是容器内 `./models`，挂载的文件找不到，属于部署缺陷）。一条命令安装：`bash scripts/install-models.sh`。服务本身不联网下载模型。

**模型后到、不用重启**：

| 项 | 行为 |
|---|---|
| 判断文件是否可用 | 每次调用都看磁盘：两个文件都在，且修改时间已超过 5 秒（`SETTLE_MS`，防止把还在复制的半截文件当成模型） |
| 版本号 | `local-text-cls-v1:<权重SHA前16位>:<词表SHA前8位>:<最大token>`；按“文件大小+修改时间”缓存，文件变了才重新计算，不再永久缓存 |
| 加载失败 | 只对**同一份文件**记住失败，换了文件立即重试，没换每 5 分钟（`RETRY_AFTER_MS`）重试；不再永久失败直到重启 |
| 换模型文件 | 发现签名变化后加载新会话；用写锁等进行中的推理结束再替换并关闭旧会话；加锁顺序统一为“先对象锁、后读写锁”，避免死锁 |
| 没有模型时 | 搜索、推荐、助手查衣柜自动降级为字段加关键词，不报错，设置页提示“智能搜索准备中” |
| 抠图模型 | 每次使用前检查文件，第一次需要时才加载；缺失时提示未安装或改用 GRABCUT |

**首次接入后的全量建索引**：

1. 后台 `SEMANTIC_INDEX` 处理器每 30 秒扫描一次：查所有用户中“没有向量、向量属于旧模型或旧衣物版本”的在架衣物（一条汇总查询）。
2. 模型刚可用时先在后台预热加载（约 1 秒），避免第一次用户查询等待。
3. 每个有待处理衣物的用户排一个低优先级 CPU 任务；任务内按 200 件一批连续执行，**一次最多 25 批（5000 件）**，不足一批即视为完成，余量留给下一次扫描。
4. 描述卡内容没变（例如只改了收藏）只更新版本号、不重新编码；新增、修改、重新识图的衣物在下一次扫描自动补上；任务幂等，可中断重来。
5. 编码速度实测每张描述卡约 1.5 毫秒（P2 基准，本机 fp32），1000 件约几秒到十几秒；索引未完成的用户在此期间继续使用降级检索。

**未覆盖**：本环境没有真实向量模型，“加载成功后热替换”只在假实现与坏文件上验证，真实模型的热替换需要在部署机上看一次日志“本地向量模型已加载”并核对设置页索引进度（见最终验收清单）。

### 8.6 设置页"穿搭画像"

1. 画像列表分组：冷却中的单品（立即恢复）、你对搭配的反馈（同类组合、两件搭配、单品、画风混搭）、颜色风格与常穿组合、很久没穿的衣物；每条都有依据，"不准确"屏蔽（`a-popconfirm`）。
2. 个人冷暖与正式程度偏移：当前值与上限、清空。
3. 推荐偏好：根据我的行为调整推荐、保留一套新尝试（`a-switch`）；配色胆量、图片画风混搭（自动学习/总是允许/总是不混，`a-segmented`）；常住城市。
4. 语义搜索严格度滑块（0~100，步长 5，默认 50 标"推荐"），当前档说明与 5 个实测档位说明，可恢复推荐档。
5. 清空画像（危险操作，确认后清空，记录本身保留）。

## 九、测试与评估

1. **单元测试**：特征派生、各打分维度、硬约束、多样化、理由核对、分词器、向量相似度。
2. **测试衣柜**：在 `src/test/resources/recommend/` 下准备 3 套固定衣柜（小：20 件、中：120 件、偏科：几乎全是运动风）。
3. **"坏搭配"断言**（每次 CI 都跑）：
   - 寒冷档推荐中不出现短裤、无袖或凉鞋；
   - 强调色数量不超过设定值；
   - 不出现两件强花纹；
   - 正式程度跨度 ≥3 的组合不出现；（P3 起以上冷暖、正式程度、鞋款兼容类断言改为"不进前 3，且出现时必带对应规则扣分与依据"，见 5.4.1）
   - 理由中的颜色词全部属于该套衣物；
   - 三套推荐的主体两两不同（库存允许时）。
4. **性能**：中等衣柜单次推荐 <200ms（不含向量编码），500 件衣柜 <500ms。
5. **语义召回评估**：准备约 50 条"查询 → 期望命中衣物"的标注对，记录前 5 名命中率，用来调门槛与权重。
6. **成本**：同一批 20 条聊天推荐请求，对比改造前后的 token 总量。
7. **好坏搭配考试题**（P4，D38）：`golden-outfits.json` 固定衣柜与 12 道人工认定的题，好搭配须 ≥60 分，坏搭配须被排除或至少低 5 分，每次构建都跑。
