## 一、一句话总结

以前：助手拿到几十套候选和全部衣物资料，由大模型"凭感觉"挑，容易乱搭、说不清理由、还费钱。

现在：**搭配由后端按规则算出来，每一分都有依据；大模型只负责听懂你说什么、把结果说成人话。** 页面上的推荐、换一批、换一件、今日灵感、衣柜搜索、取色全部本地计算，不花模型费用。

## 二、整体是怎么工作的

```
你的要求（页面意图条 / 跟助手说话）
  → ① 整理成结构化条件：场景、温度（不填就查常住城市天气，再不行按日期推断季节）、想要/避开的颜色、风格描述、必选/排除的衣物
  → ② 按位置挑候选：上装、下装、连衣裙、鞋分别从你的衣柜里挑（字段 + 关键词 + 本地语义理解）
  → ③ 组合并过"底线规则"：结构不完整、你明确说过不要的、男性配女款 → 直接不要
  → ④ 白盒打分（满分 100）：七个维度 + 扣分项 + 搭法模板加分 + 你的个人偏好，每一项都写依据
  → ⑤ 挑出彼此不重样的几套，生成理由（理由里的颜色、品类必须真的属于这套衣服）
  → 展示卡片；你的点赞/点踩/换一件/打卡再回流到"穿搭画像"，影响下一次
```

七个打分维度：配色、冷暖、正式程度、风格统一、季节、个人偏好、新鲜度（不总推同几件）。

## 三、各期做了什么

### P1 推荐引擎（地基）

| 功能 | 干什么的 |
|---|---|
| 推荐引擎 | 上面第二节的整条流水线：意图、特征、召回、规则、打分、多样化、理由 |
| 理由核对 | 防止"白衬衫配黑裤子"这种理由里出现衣服里根本没有的颜色或品类 |
| "新尝试"位 | 三套里固定一套稍微不一样的，避免永远只推安全牌；可关闭 |
| 建议外层 | 天冷时单独建议一件外套，不混进组合 |
| 穿搭画像（基础版） | 从收藏、已保存搭配、OOTD、记忆里统计你常穿的颜色、风格、单品 |
| 助手改造 | 助手改用 `recommend_outfits` 工具：只拿到 3~5 套的要点，不再拿全部衣物资料 |
| 推荐卡片 | 助手里的卡片：总分、亮点、提示、得分明细、每件为什么入选、👍/👎 |

效果：给模型的内容减少约 95%，一轮推荐的模型调用从 3 次降到 2 次；500 件衣柜单次推荐 86 ms。

### P2 本地语义理解

| 功能 | 干什么的 |
|---|---|
| 本地向量模型 | 让系统听懂"适合海边的""文艺一点""那件小熊卫衣"这种字段表达不了的说法；模型在服务器本地运行，零 API 费用，数据不出服务器 |
| 衣柜语义搜索 | 衣柜搜索框升级：颜色、品类按字段精确筛，描述按语义找，找不到就如实说"没有"，并告诉你最接近的是哪件 |
| 推荐里的语义召回 | 推荐时也能按描述挑衣服，卡片写明"语义'文艺一点' 0.42" |

评估：53 条标注查询，前 5 名命中 95.3%，"衣柜里没有"的查询 100% 正确返回空。

### P3 规则收敛、反馈学习与页面闭环

| 功能 | 干什么的 |
|---|---|
| 硬规则只留底线 | 只有三类直接排除：结构不完整、你明确说过的（排除、避开颜色、记忆里"不穿"、冷却中的单品）、男性配女款。其余（如女生高跟鞋配牛仔裤）都改成扣分并写明原因，让引擎综合判断，避免一刀切 |
| 规则追踪与"为什么没推荐它" | 每次推荐记录每件衣服被排除/截断/入选的原因；详情页、衣物页、助手都能用大白话回答 |
| 反馈三层 + 衰减 + 冷却 | 一次不喜欢同时记在"整套""两两组合""同类组合"上；30 天影响减半；不喜欢两次进冷却期（不是永久拉黑），可估计恢复时间、可立即恢复 |
| 个人偏移与闲置激活 | 常说"太热/太正式"会形成可清空的偏移；30 天没穿的衣服小幅加分 |
| 画面风格录入时判断 | 识图时顺便判断展示图是写实/卡通/线稿，不额外收费；混搭偏好自动学习 |
| 语义搜索严格度滑块 | 设置里 0~100 可调，默认 50 是实测最佳档 |
| 组合台"今天穿什么" | 意图条 + 3 张卡 + 换一批 + 换一件 + 今天穿了（打卡） |
| 设置页"穿搭画像" | 每一条画像都能看到依据、单独屏蔽，可一键清空 |
| 模板审核页 | 管理员逐条或批量审核搭法模板 |

## 五、精确取色是干什么的？换了图片颜色信息会不会过时？

### 是干什么的

衣物的颜色原本只有识图给的一个**颜色名**（例如"蓝色"）。颜色名很粗：雾霾蓝和宝蓝都叫"蓝色"，前者其实接近灰色，后者很鲜艳。只按颜色名判断，会把"雾霾蓝上衣 + 卡其裤"误判为"两个强调色撞色"。

精确取色做的事：后台直接读展示图的像素，算出这件衣服主要颜色的**深浅、鲜艳程度和色相**（CIELAB 色彩空间，纯本地计算）。一套衣服每件都取过色后，打分会多参考这些实测值：

- 上下深浅分明 → 小加分（层次清楚）；
- 两件都很鲜艳、色相相反、深浅又差不多 → 扣分（对比过强）；
- 色相相近 → 小加分（同色系和谐）；
- 识图说是彩色、实测其实很灰 → 按中性色处理，不再当成"强调色"。

这些调整幅度都很小，颜色名规则仍然是主力；没取完色的衣服完全按原来的方式判断，所以不会出现新旧数据混在一起时分数乱跳。

### 换了图片会不会过时？

分两部分回答：

1. **实测颜色不会过时。** 每条取色结果都记着"是用哪张展示图算的"。展示图一换（重新生成、手动选另一张、恢复等），旧结果立刻不再使用，后台任务（每 30 秒扫描一次）发现后按新图重算；算好之前这件衣服按"未测色"处理。
2. **识图给的颜色名不会跟着自动改。** 换展示图不会重新识图，所以"主色"这个字段（例如"蓝色"）保持不变。一般情况下换的是同一件衣服的另一张图，颜色名本来就不该变；但如果识图当初认错了颜色，或者新图的颜色和旧名明显不符，颜色名仍会是旧的。精确取色只能纠正"其实很灰"这一类偏差，**不会**把"蓝色"改成"绿色"，因为颜色名可能是你手动确认过的。

遇到颜色名不对时：在衣物详情里手动改主色，或对这件衣服重新识图。

可以做但这次没做的改进（已写进后续池思路）：当实测色相和颜色名明显不一致时，在衣物页提示"实测颜色和记录的不一致，要不要更新"，由你确认后再改。

## 七、需要你处理的事

1. **审核模板**：66 条（58 经典 + 8 流行）全部待审核。不审核也能推荐，只是没有"经典搭法"加分，今日灵感为空。
2. **天气**：部署机器放行 `geocoding-api.open-meteo.com`、`api.open-meteo.com`，并在设置里填常住城市。
3. **向量模型**：在宿主机执行 `bash scripts/install-models.sh`（抠图与向量两个模型，服务不会自动下载）。**容器可以先启动、模型之后再装，不用重启**：文件放好 5 秒后自动加载，后台 30 秒内开始为所有用户的全部衣物建向量（一次任务最多 5000 件），其间搜索与推荐降级为字段 + 关键词。细节见总设计 5.21。验收时看日志有“本地向量模型已加载”，设置页索引进度走满。
4. **合并**：确认后把 `feat/outfit-recommend-p4` 合并到前后端的 main（它包含 P3）。
