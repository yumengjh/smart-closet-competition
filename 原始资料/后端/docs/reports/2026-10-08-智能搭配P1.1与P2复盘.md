## 三、用户实测反馈逐条复盘

### 3.1 推荐出"高跟鞋 + 衬衫 + 长裤"，不分男女

- **现象**：三套推荐都带同一双红色高跟鞋，配休闲长裤。
- **根因**：P1 完全没有"鞋款 × 下装 × 场景"的判断，也不读性别；正式程度跨度只有 1.75（<2 不扣分）；红色单一强调色反而在色彩维度加分；这双鞋是衣柜里唯一的鞋，多样化只看主体不看鞋，所以三套都用它。
- **修复**：配置化兼容表（OK/扣分/排除）、只读性别、未设性别时最保守、推测依据只扣分、必选时尊重用户。
- **过程中的修正**：用户补充"女装里高跟鞋配裤装有时可以"，规则从"高跟鞋配任何裤装都排除"改为按性别、场景、裤型分层。说明这类审美规则**必须让用户先拍板边界**，不能由实现方一刀切。
- **验证**：坏搭配断言（男性无女款、未设性别不配裤装、女性不配运动裤、运动户外居家无高跟鞋、女性通勤可配西裤）+ 真实数据复核。

### 3.2 三次"不喜欢那双鞋"，仍然被推荐

- **根因**：明确的"不喜欢"也被当作统计信号，要过 3 条证据门槛、还被平滑；每次 −2.5 除以（次数 + 3），最终只轻微影响召回和偏好分；而鞋位只有这一双，召回截断不会剔除它；"换一批"用的是空画像。
- **修复**：首次即降到 −0.6；60 天内 ≥2 次暂停并可恢复；组合否定按不同衣物对计数；换一批用当前画像重新核对打分。
- **教训**：**"明确表达"和"行为统计"是两种信号**，前者应立即、确定地生效，后者才需要门槛和平滑。

### 3.3 "重新搭配"被拒，还让用户去别的页面

- **根因**：意图门控只用正则看当前这一句，"重新搭配"没匹配上，本轮没开放推荐工具；提示词又允许模型"引导用户"。
- **第一次修复**：扩充说法 + 结合会话上下文 + `basedOnPrevious` 沿用条件 + 提示词禁止"去别的页面"。
- **后来发现仍然不够**：用户说"帮我发一套比较可爱的穿搭""我想要千金风的穿搭"，正则依然漏掉，模型又按提示词"说明如何明确表达"，让用户换说法——恰好是用户最反感的。
- **最终修复**：推荐卡片工具**始终开放**（它只出卡片、不写数据），只有打开到画板这种写操作需要识别意图；提示词改为"想要穿搭就直接推荐，不要让用户换说法"。
- **教训**：**门控应按"有没有副作用"来设计，而不是按"能不能猜出意图"。**只读、可撤回的能力不该被正则卡住；要卡的是写操作。

### 3.4 图片风格不同的衣物能不能同套

- **需求**：衣柜大多是写实实物图，少数是卡通插画、简笔线稿；以后可能整体卡通化。搜索默认看占多数的风格。
- **决策**：风格挂在**展示图**上（不是衣物本身），换展示图自动重判；用识图服务，12 张拼一张编号网格判一次，计 1 次额度，不改其他字段；用户手动设置优先。
- **验证**：真实衣柜 48 件 4 次调用，与人工看图基本一致；用户账号下 HTTP 实测默认范围与切换。

### 3.5 "可爱穿搭"推得很差

用户原对话四轮：第一句没出推荐；补"可爱风"后推 T 恤配长裤；问"不是有更好看的裙子吗"只得到反问；说"你来搭配"仍推半身裙配 T 恤。

| 原因 | 修复 |
|---|---|
| 门控没覆盖"发一套…穿搭" | 补说法，后来改为推荐工具始终开放（3.3） |
| "可爱"不在风格词表，衣物上标的是"甜美/洛丽塔" | 风格同义词表；衣物自定义标签同样映射 |
| 想要的风格只影响已经封顶（满分 1）的维度分，甜美连衣裙得不到额外加分 | 明确愿望在总分上单独加减（+6/−6），满足时作为第一条亮点 |
| 连衣裙作为单件主体被算作"风格标签不足"（0.7） | 单件主体改为"一件成型，风格统一" |
| 没有"想穿裙子"的条件，模型只能反问 | 新增 `wantCategories`，提示词要求直接重新推荐 |

- **怎么发现封顶问题的**：单测"可爱→甜美排第一"是绿的，但接口返回仍是 T 恤长裤。直接看每套各维度得分，才发现愿望加分被 `clamp(1)` 吃掉。**教训：调分数时要看最终总分和排名，不能只看某个维度有没有加分。**
- **验证方式升级**：写了 `scripts/agent-chat-eval.py`，用真实模型、真实账号、包括用户原话四轮的场景自动判定。第一次跑出 9/10，唯一失败是判定条件写死了"至少 2 套甜美"，而用户说"一套"时模型合理地只给了 1 套——**评估脚本本身也要接受"什么才算对"的审视**。

### 3.6 "映射是不是只是文字匹配？以后有新词怎么办？"

- **诚实回答**：当时确实只是词表（包含匹配），词表外的词只当描述，效果弱，没有彻底解决。
- **实验 1**：新词对"风格描述句"做向量比对——非风格词（价格 0.62、苹果 0.57）和真风格词分数一样高，不可用。
- **实验 2**：新词对"每个风格十来个示例词"做近邻——能判对具体词（瑜伽、晚宴、面试、露营、芭蕾），不懂时尚说法（千金、多巴胺、美拉德、港风、老钱、JK）。
- **意外发现**：示例词里放了和评估词相同的五个词（泄题），去掉后重测结论不变，但这次差点用"作弊"的数字做决定。**教训：评估集和"训练"用的词表必须互不重叠，并在测试里断言。**
- **最终方案**：三层——词表 → 聊天中模型在**同一次调用**里顺带归类并记入词库 → 本地近邻（只在领先 ≥0.14 时）→ 交给描述语义。零额外模型调用，词库越用越全。
- **实测**：千金风、多巴胺风、来点甜的，都直接推荐甜美连衣裙；词库学会千金→甜美/正式、多巴胺→甜美；随后页面接口直接可用。

### 3.7 "搜索也能用吗？搜索框加个说明图标"

- **根因**：搜索只认"甜美"这类标准词，"可爱"只当描述算相似度。
- **修复**：搜索接入同一套三层归类；风格作为筛选，原话用于排序；风格条件下的残余词（"场合""上班穿"）只排序不卡门槛；本地近邻只用于"××风/××系"的明确说法；搜索框加问号说明与可点示例。
- **过程中的回退**：接入后评估命中率先从 93.0% 掉到 90.7%，再掉到 88.4%，逐条看未命中才找到原因（描述被清空后失去排序；标准风格词没被剥离；残余词仍卡门槛），修完升到 95.3%。**教训：每改一次搜索规则都重跑评估，并逐条看未命中，不看平均数。**

## 四、过程问题与教训

| 问题 | 发生了什么 | 处理 | 以后怎么做 |
|---|---|---|---|
| 发布脚本写死路径 | worktree 的前端产物被发布到 main 的 static | 先手工同步并恢复 main；后改脚本支持 `CLOSET_SERVER_DIR` | 构建脚本里不写死相邻目录 |
| 守护服务抢端口 | 停掉 main 后 launchd 立刻重启它，分支服务启动失败 | 找到 `com.smartcloset.server.lan` 并移除，记录恢复命令 | 部署前先查端口的守护者 |
| 健康检查走代理 | 手动启动时 curl 走代理，返回 502/失败 | 加 `NO_PROXY` | 本机脚本统一 `--noproxy` |
| Codex 沙箱限制 | 无网络、不能写 worktree 的 git 元数据、本地起服务的测试跑不了 | 主会话接手下载、对拍、基准、测试与提交 | 委派前先确认执行环境；需要网络和提交的步骤留在主会话 |
| Codex 改反了方向 | 把"能不能重新搭配"一律判为能力询问，正是用户抱怨的反方向 | 复核时改回，并按上下文区分 | 委派结果必须逐行复核，尤其是与用户反馈直接相关的部分 |
| Codex 的测试没在沙箱跑过 | 新测试用随机衣物 ID，在真实环境报"没有找到会话" | 改用真实衣物 | 不信任未运行过的测试 |
| CPU 吃满 | 两个 Codex 各跑一份 Maven，用户使用卡顿 | nice 20 + 后台 QoS 守护脚本；之后构建串行、低优先级 | 并行任务的重计算要排队或降级；用户机器优先 |
| 测试不稳定 | 两条消息同一毫秒写入，按时间排序先后随机 | 测试中间隔几毫秒 | 依赖时间排序的测试要显式拉开时间 |
| 测试中工具次数超限 | 在已有用例里多加一次工具调用，触发本轮上限 | 去掉 | 往已有集成测试里加断言前看清预算 |
| `Map.of().containsKey(null)` 空指针 | 未判定图片风格的衣物导致整套推荐 500 | 判空 | 不可变集合不接受 null 查询 |
| 门槛定高 | 设计初值 0.5 下描述类几乎全不命中 | 用评估集校准 | 门槛一律由评估决定，不拍脑袋 |
| 关键词按大类误命中 | "领带"按"配饰"大类命中围巾、包、帽子 | 精确关键词只认字面 | 兼容旧行为时先确认旧行为的真实语义 |
| 残余单字 | "小白鞋"解析后剩"小"，被当描述导致零结果 | 单字残余视为空 | 解析器要测"所有字都被吃掉"的边界 |
| 提示自相矛盾 | "相似度 0.40，低于门槛 0.35" | 区分"低于门槛"和"区分不明显" | 提示文案要说真实原因 |
| 硬条件被描述藏起来 | "适合海边的白色上衣"返回零，提示"没有白色上衣"，实际有 3 件 | 有硬条件时描述只排序 | 用户的硬条件优先于模糊描述 |
| 评估泄题 | 风格示例词包含评估词 | 删除后重测 | 评估词与示例词互斥 |
| 误提交构建产物 | `git add -A src` 把 static 下的 `manifest.webmanifest`、`sw.js` 提交了 | 撤出并加入忽略 | 不用 `git add -A` 加整个目录；提交前看 `git diff --stat` |
| 用掉用户对话额度 | 对话评估用光当天 30 次，接口返回 429 | 测试部署临时调到 200 | 跑真实模型评估前先估算次数，告知用户 |
| 初始密码失效 | 无法 HTTP 登录自测 | 先用复制数据库在服务层验证；用户授权后再走 HTTP | 自测账号与凭据提前约定 |
| 中途被打断 | 工具调用被拒后按规则停下，用户问"你怎么停了" | 说明原因后继续 | 被拒时一句话说明原因再等 |

## 五、做得好的地方

- **先复现再改**：A、B 都先查数据库确认根因（唯一一双鞋、三条反馈都已落库），没有凭猜测改代码。
- **白盒依据**：每个扣分、排除、风格归类都有文字依据，用户和开发都能看懂为什么。
- **零额外模型成本**：语义、搜索、风格近邻都在本机；需要常识的风格归类借用聊天中本来就有的那次调用；图片风格 12 张一次。
- **诚实回答"没解决"**：用户追问映射是否只是文字匹配时，先承认不足，再用实验说明边界和方案。
- **评估驱动**：搜索门槛、风格近邻门槛、对话行为都有可重复的评估，并在测试里加了护栏。
- **用户机器的体验**：发现 CPU 问题后立刻降级，后续所有构建都低优先级串行。

## 六、沉淀的做法（建议写入项目约定）

1. **门控按副作用设计**：只读、可撤回的能力默认开放，写操作才要求明确意图。
2. **明确表达立即生效**：用户说的"不喜欢/想要/不穿"不走统计门槛。
3. **审美规则由用户拍板边界**，配置化、带版本、可解释。
4. **改搜索或打分后必须重跑评估并逐条看未命中**；门槛只由评估决定。
5. **评估集与规则词表互斥**，在测试里断言。
6. **真实模型对话评估**作为助手改动的验收：包含用户原话，检查工具、卡片和"推脱话术"。
7. **本地小模型能力有边界**：先实验确认它懂什么，再决定让它承担多少；不懂的交给本来就在调用的大模型并缓存结果。
8. **委派给其他代理的结果必须复核**，并在主环境运行全部测试后才提交。
9. **重计算任务低优先级、串行**，不在用户机器上并行跑多份构建。
10. **提交前看改动清单**，不整目录 `git add -A`。
