# 图文模型、超级搜索与重复提醒报告（2026-10-09）

设计：[模型内存管理与图像向量设计](../../docs/design/2026-10-09-模型内存管理与图像向量设计.md)（G1~G17）。测试流程：[docs/IMAGE_SEARCH_TESTING.md](../../docs/IMAGE_SEARCH_TESTING.md)。分支：前后端均为 `feat/image-search`（后端基于 `feat/model-memory`，前端基于 `feat/similar-garments`），**未合并到 main**。

## 一、按你的决定做了什么

| 决定 | 实现 |
|---|---|
| 要“文字找图片”，模型不能太差 | Chinese-CLIP ViT-B/16（中文图文同一空间，188M 参数）；`scripts/export-image-model.sh` 从官方权重导出 ONNX（fp32 + int8），逐文件与 PyTorch 对拍后才放入 `./models` |
| 只用于相似提示和搜图 | 相似度新增“图像”一项（约占 35%）；可能重复新增“图像几乎一样 → 同一件的不同照片”；推荐不变 |
| 搜图与现有以图搜图合并 | 衣柜页一个搜索框：文字 / 图片（相机、粘贴、拖入）/ 图片 + 文字；新接口 `POST /api/garments/search`，与文字搜索同一结果格式；文字搜索也会直接和图片比对（理由“图片像…”）；原“以图搜图”弹窗去掉 |
| 判出重复就通知，放右上角 | 新增站内通知（`/api/notifications`），在“处理中心”铃铛里单独一组“提醒”，未读计入小圆点，新提醒弹一次；`NotificationChannel` 接口预留邮件 |
| 入柜时自动判断，不做定时扫描，手动一键扫描 | 入柜后处理流程新增 `IMAGE_INDEX`（图像向量）与 `DUPLICATE_CHECK`（每件只查一次，同一对只提醒一次，4 件以上合成一条汇总）；升级时旧衣物记为已检查，不会冒出旧提醒；“整理衣柜”加“一键扫描整个衣柜”（后台任务，完成后提醒） |
| 内存紧张自动回退，但要提示 | 加载前查可用内存（容器内按 cgroup），不够就不加载；所有相关接口返回 `imageModel.state/message`，前端在搜索、整理衣柜、相似面板显示；运维状态报 `IMAGE_MODEL_LOW_MEMORY` |
| 入柜就算 | 图像向量在入柜后几十秒内由后台单线程算好（低优先级） |
| 只用允许商用的 | Chinese-CLIP 仓库为 MIT；权重由同一项目发布、未单独声明许可证，已在 `models/README.md` 如实写明，建议商用前再确认 |
| Java 堆不限制 | 未改 |

## 二、实测（本机 4 核、2 推理线程；真实结构 + 随机权重，只测速度、内存与一致性）

这个环境连不上模型下载站，拿不到官方权重，所以用 ViT-B/16 的真实网络结构加随机权重跑通了整条导出链路，并测了速度和内存。**效果要你用真实权重评估**（第四节）。

| 项 | 结果 |
|---|---|
| 导出链路（导出 → int8 量化 → PyTorch 对拍 → 清单） | 通过，约 30 秒；int8 图像塔 87 MB、文本塔 102 MB |
| Java 预处理 + 分词 + ONNX 与 PyTorch 一致度 | fp32：图像 1.00000、文字 1.00000；int8：图像 0.99985、文字 0.99925 |
| 预处理与官方逐像素对拍 | Pillow 双三次缩放最大差 1 级灰度，≥ 99% 完全相同 |
| 分词与官方 cn_clip 对拍 | 18 条（中英混排、全角、表情、超长）全部一致 |
| 内存（模型增加的进程常驻内存） | 图像 int8 + 文字 int8：约 340 MB；图像 fp32 + 文字 int8：约 670 MB |
| 单张图像编码 | int8 约 130 ms，fp32 约 280 ms；文字约 100 ms |

**2026-10-10 用真实权重复测（issue #15）**：真实权重下，按张量量化的文本塔最差一句只有 0.82（Java 对拍 0.853），表中 0.99925 是随机权重的结果，不能代表真实权重。导出脚本改为文本塔按通道量化后，PyTorch 对拍最差 0.970，Java 对拍 0.970，40 条服饰查询平均 0.987，文件 103 MB。图像塔不变（0.972，Java 0.963），哈希不变。

据此把默认图像塔从原计划的 fp32 改为 **int8**（省一半内存、快一倍、一致度 0.9998）；评估工具会同时比较两档，效果差得明显就切回 fp32。

## 四、需要你做的

1. 按 [测试流程](../../docs/IMAGE_SEARCH_TESTING.md) 在 MacBook 导出模型、本地测试。
2. 用 30~100 件真实衣物跑评估（第 8 节），把 `target/image-eval/report.md` 发我，我据此定门槛（同一件 0.93、文字找图片 0.25/0.05/0.06 都是初始值）和 int8/fp32。
3. 部署到 4G 服务器后记下 `processRssBytes` 与 `free -m`，校准内存预算。
4. 合并：本分支在 `feat/model-memory` 之上，确认后合并。
